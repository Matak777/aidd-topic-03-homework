# FEATURES.md — задание №4: новая функциональность

Документ формулирует функциональные требования к четырём группам из
HOMEWORK.md (задание №4), критерии приёмки, изменения модели данных и план
интеграции. Реализация идёт по этапам: после каждого этапа приложение
остаётся работоспособным. Текущий статус реализации указан в §5.

Общие принципы, действующие для всех групп:

- Все сделки — **исключительно виртуальные**: реальные ордера не отправляются
  ни при каких настройках (SDK-клиенты ордеров не вызываются).
- Живой Tinkoff API и Redis недоступны в среде. Подменённые данные не
  выдаются за живые котировки: любая недоступность интеграции показывается
  пользователю честно; для воспроизводимой демонстрации существует
  **явно включаемый** demo-режим с пометкой источника данных в БД и в
  интерфейсе.
- Цены внутри доменной логики хранятся и вычисляются точно (`Decimal` через
  exact-преобразование units/nano из gRPC `Quotation`); `Float` остаётся
  только в существующих полях `Share.last_price` (совместимость).

## 1. Группа 1: персональный мониторинг акций (списки, цели, уведомления)

### Требования

- **F1.1 Watchlists.** Аутентифицированный пользователь может создавать
  именованные списки наблюдения, добавлять/удалять в них акции из каталога,
  просматривать свои списки. Акция добавляется по одному разу на список.
- **F1.2 Целевые цены.** Для каждого элемента списка можно задать целевую
  цену и направление условия: «цена ≥ цели» (продажа/взять прибыль) или
  «цена ≤ цели» (затариться). Можно задать обе цели.
- **F1.3 Уведомления без повторов.** При переходе цены через цель
  создаётся уведомление пользователя. Событие фиксируется один раз: пока
  условие не отредактировано и не «перевзведено», повторов одного и того же
  уведомления нет. Уведомления видны списком с отметкой прочитанных.
- **F1.4 Автоматическая проверка.** Условия проверяются автоматически на
  базе накопленных наблюдений цен (группа 3) — тем же локальным
  периодическим процессом/фоновым механизмом, без обязательного Redis
  (проверка только по БД, внешние RPC не нужны).

### Критерии приёмки

1. Список виден только владельцу; другие пользователи его не видят и не
   редактируют (проверка тестом).
2. Повторное добавление той же акции в тот же список даёт ошибку валидации,
   а не дубль.
3. Уведомление создаётся один раз на событие: повторная обработка того же
   наблюдения не создаёт копий (тест с двойным запуском проверки).
4. Смена цели «перевзводит» условие (новое событие возможно).
5. При пустой базе наблюдений проверка условий ничего не делает и не падает.

### Изменения модели данных

- `WatchList`: `user` (FK User, related_name="watchlists"), `name`
  (CharField), `created_at`. Уникальность `(user, name)`.
- `WatchItem`: `watch_list` (FK, CASCADE), `share` (FK Share),
  `target_high` (Decimal null — цель сверху), `target_low` (Decimal null —
  цель снизу), `notes`, `created_at`; уникальность `(watch_list, share)`;
  Decimal по той же схеме точности, что и наблюдения.
- `Notification`: `user` (FK), `watch_item` (FK, CASCADE),
  `condition_key` (CharField — сериализованный ключ события: направление +
  значение цели),
  `message`, `triggered_price` (Decimal), `triggered_at` (auto_now_add),
  `is_read` (bool). Уникальность `(watch_item, condition_key)` — механизм
  «без повторов»: состояние события = конкретная цель + направление;
  редактирование цели меняет ключ события и тем самым перевзводит условие.
- Проверка условий: сервис `check_watch_targets()` — читает последние
  наблюдения из БД, сравнивает с целями, создаёт уведомления; идемпотентность
  обеспечивается unique-ограничением, проверка работает только на
  локальной БД.

### План интеграции

1. Модели WatchList/WatchItem/Notification + миграция.
2. Views/forms: CRUD списков и элементов (только владелец), страница
   уведомлений + счётчик непрочитанных в base.html.
3. Проверка условий — расширение локального коллектора (та же management
   command, этап: после сохранения наблюдений).
4. Celery-задача-обёртка той же проверки (опционально, как для группы 3).

## 2. Группа 2: виртуальный инвестиционный портфель

### Требования

- **F2.1 Портфели.** Аутентифицированный пользователь создаёт именованные
  виртуальные портфели (несколько на пользователя).
- **F2.2 Сделки.** В портфеле регистрируются виртуальные покупки/продажи
  акций каталога: сторона (buy/sell), количество (> 0), цена сделки
  (заполняется текущей ценой из БД по умолчанию, редактируемая). Реально
  ордера не отправляются ни при каких настройках.
- **F2.3 Агрегаты.** По каждой позиции показывается чистое количество и
  средняя цена приобретения (взвешенная); по портфелю — текущая стоимость
  (по последней сохранённой цене каждого инструмента из БД наблюдений) и
  прибыль/убыток: нереализованный (опен-позиции) и реализованный (по
  продажам), в денежном выражении и в процентах.
- **F2.4 История операций.** Журнал сделок портфеля с пагинацией.

### Критерии приёмки

1. Две покупки 10 шт по 100 и 10 шт по 110 → 20 шт, средняя 105.0 (тест).
2. Продажа части позиции уменьшает количество, не меняет среднюю цену,
   увеличивает реализованный P/L (тест).
3. Продажа больше количества позиции запрещена (валидация, тест).
4. Текущая стоимость считается из сохранённых наблюдений (последняя цена
   инструмента в БД); при отсутствии наблюдений позиция в расчёте не
   участвует, но помечена как «без цены» (тест).
5. Портфель/журнал видны только владельцу (тест).
6. В журнале и агрегатах — Decimal, без плавающей арифметики.

### Изменения модели данных

- `Portfolio`: `user` (FK), `name` (CharField), `base_currency`
  (CharField, по умолчанию из настройки), `created_at`; уникальность
  `(user, name)`.
- `Trade`: `portfolio` (FK CASCADE), `share` (FK PROTECT), `side`
  (buy/sell), `quantity` (Decimal > 0), `price` (Decimal > 0), `created_at`
  (auto_now_add), `note`. Агрегаты считаются из Trades (quantity -
  сумма покупок − продаж; средняя — по покупкам с остатками; реализованный
  P/L — FIFO/средняя-себестоимость, определяется при реализации этапа).
- `Position` не хранится, а вычисляется (агрегирование
  из `Trade` на лету) — исключает рассинхрон «журнальных» и «агрегатных» данных.

### План интеграции

1. Модели Portfolio/Trade + миграция; валидаторы количества/балованса.
2. Views: портфели, журнал, форма сделки с подстановкой текущей цены;
   панель агрегатов на странице портфеля.
3. Страница портфеля показывает процентные и абсолютные P/L; в пустых
   случаях — осмысленные заглушки.

## 3. Группа 3: история изменения рыночных цен (этап 1 — реализуется сейчас)

### Требования

- **F3.1 Накопление.** Рыночные цены всех акций каталога автоматически
  сохраняются в БД: точная цена (Decimal из units/nano), инструмент,
  валюта, время котировки и время получения, источник данных.
- **F3.2 Дедупликация доставки.** Повторная доставка одного наблюдения не
  создаёт дубликат; одинаковая цена в разное время сохраняется как разные
  наблюдения.
- **F3.3 Периодический сбор без Redis.** Локальный управляемый процесс
  (management command) с настраиваемым интервалом, обработкой ошибок и
  штатной остановкой; собирает цены через те же сервисы SDK, что и
  существующая задача Celery (обязательность Redis сохраняется
  опциональной).
- **F3.4 Просмотр истории.** Доступная из интерфейса страница истории
  акции: выбор периода, список наблюдений, абсолютное и процентное
  изменение, график из накопленных данных.
- **F3.5 Демонстрационный источник.** Явно включаемый demo-режим
  (без токена): синтетические цены, помеченные источником `demo`, и
  пометка «демонстрационные данные» в интерфейсе. Обычный режим без токена
  честно показывает недоступность интеграции.

### Критерии приёмки

1. Точность: Quotation(units=123, nano=450000000) → Decimal("123.45")
   (тест; никакой float-арифметики при записи).
2. Повторная доставка: два наблюдения на один (share, quote_time, source)
   → одна строка (тест с двойным сохранением).
3. Одинаковая цена в разное время → две строки (тест).
4. `quote_time` и `received_at` — разные поля; получатель не переписывает
   время котировки (тест).
5. Коллектор: 3 цикла с --max-cycles создают накопление, интервал/очередь
   обрабатывают сбой источника без падения процесса (тест).
6. Страница истории: пустая история/одна точка/нулевая начальная цена/
   неверный период/отсутствующий инструмент — явные состояния без 500
   (тесты на все).
7. График строится из БД (без внешних RPC) при ≥2 точках; для 0/1 точек —
   явное сообщение.
8. Demo-режим включается только явной настройкой; источник отмечается в БД
   и заметен пользователю (тест + интерфейс).

### Изменения модели данных (этап 1 — сделано)

- `PriceObservation`:
  - `share` (FK Share, CASCADE, related_name="price_observations"),
  - `price` (CharField(40) — точная цена как текст десятичного числа;
    NUMERIC-представление на SQLite молча округляло, текст даёт точный
    roundtrip; миграция 0009 перенесла данные),
  - `currency` (CharField(20) — валюта наблюдения),
  - `source` (CharField(20), choices tinkoff/demo — происхождение),
  - `quote_time` (DateTimeField — время котировки от источника),
  - `received_at` (DateTimeField(auto_now_add=true) — время получения).
  - Уникальность `(share, source, quote_time)` — ключ дедупликации
    доставки: повторная доставка того же наблюдения (тот же источник и
    то же время котировки) не создаёт вторую строку; get_or_create —
    идемпотентно (первая копия выигрывает). Одна и та же цена в другое
    время — другая строка (другой quote_time).
  - Индекс `(share, quote_time)` для выборок по периоду.
- `Share` (дополнения этапа 1): `last_price_source` (CharField(20)
  null — tinkoff/demo/manual; NULL — происхождение неизвестно, честно
  показывается пользователю).

### План интеграции (этап 1 — сделано)

- `services/price_history.py`: `quotation_to_decimal` (exact units/nano),
  `record_observations` (дедуплицированная запись), провайдеры цен
  (`tinkoff` — через существующий `get_last_prices` с RPC-дедлайном,
  `demo` — детерминированный синтетический генератор), `collect_cycle`
  (один цикл сбора), расчёты истории и график из БД.
- `manage.py collect_prices --interval N --source tinkoff|demo --max-cycles N`
  — локальный периодический сбор; ошибки цикла технологуются и цикл
  продолжается; `KeyboardInterrupt`/`SIGTERM` — штатная остановка.
- Celery сохранён: задача `update_last_price` дополнительно пишет
  наблюдения (этот же источник данных).
- Страница `<id>/history?period=...` (dashboard.urls смонтированы в корне
  config.urls — префикса `share/` нет) + ссылки с карточки и списка;
  настройка `PRICE_SOURCE` (tinkoff|demo) и `PRICE_COLLECT_INTERVAL`.

## 4. Группа 4: симулятор инвестиционных стратегий

### Требования

- **F4.1 Стратегии.** Аутентифицированный пользователь создаёт именованную
  стратегию (несколько на пользователя): инструмент, тип условия
  («цена ≥ X», «цена ≤ X», «изменение за период ≥ Y%»), действие (виртуальная
  покупка/продажа заданного количества), целевой портфель (группа 2).
- **F4.2 Автосделки.** При выполнении условия стратегия автоматически
  создаёт виртуальную сделку в привязанном портфеле. Условие выполняется
  один раз (не генерирует сделки на каждом цикле), для повторного срабатывания
  стратегия должна быть отредактирована/перевзведена.
- **F4.3 Журнал.** Каждое срабатывание записывается в журнал стратегии:
  время, условие, снимок цены, созданная сделка.
- **F4.4 Оценка.** Для стратегии показывается суммарная эффективность:
  виртуальные сделки → позиция/закрытый P/L по данным портфеля +
  текущие цены из БД наблюдений. Требование наблюдений — к группе 3.
- **F4.5 Управление.** Стратегию можно включать/выключать; выключенная не
  срабатывает.

### Критерии приёмки

1. Условие «цена ≥ X» на наблюдении цены ≥ X срабатывает ровно один раз
   на данный ключ условия (тест с двумя последовательными проверками).
2. Выключенная стратегия не срабатывает (тест).
3. Сделка создаётся виртуально: только в портфеле, никаких обращений к
   ордерам SDK (тест: mock SDK-ордера отсутствует).
4. Некорректная стратегия (отрицательное количество/неизвестное условие)
   не создаётся (валидация).
5. Эффективность считается из виртуальных сделок и наблюдений; при пустой
   истории — заглушка.

### Изменения модели данных

- `Strategy`: `user` (FK), `name`, `share` (FK PROTECT), `condition_type`
  (price_above/price_below/price_change_pct), `condition_value` (Decimal),
  `action` (buy/sell), `quantity` (Decimal > 0), `portfolio` (FK Portfolio,
  null — если группа 2 ещё не наполнена), `enabled` (bool),
  `max_executions` (int, по умолчанию 1), `created_at`.
- `StrategyExecution`: `strategy` (FK CASCADE), `condition_key`
  (CharField), `triggered_price` (Decimal), `quote_time`, `trade` (FK Trade,
  null, SET_NULL), `executed_at` (auto_now_add); уникальность
  `(strategy, condition_key)` — защита от повторного срабатывания
  того же условия; ключевая величина события — «условие + целевой уровень».

### План интеграции

1. Модели Strategy/StrategyExecution + миграция (после этапа 2).
2. Сервис `run_strategies()`: читает последние наблюдения из БД, для всех
   активных стратегий проверяет условия и создаёт исполнения (и сделки);
   идемпотентность — уникальность «сигнатуры».
3. Точка вызова — тот же локальный коллектор (опция `--run-strategies`)
   и/или Celery beat; внешние RPC не нужны.
4. Views: формы настроек стратегии, страницы журнала и эффективности;
   ссылка из портфеля.

### Уточнения после повторной независимой проверки (подтверждены тестами и HTTP)

- Источник ручной цены в HTML определяет сервер: `last_price_source`

- Очистка цены снимает источник согласованно во всех путях (HTML, admin,

- Нулевая цена имеет пометку источника (проверка значения, не истинности)
  на карточке и в списке.
- `apply_prices` записывает кеш/источник/тренд/время и наблюдение атомарно
  на инструмент (`transaction.atomic`): при сбое записи наблюдения кеш
  откатывается и не остаётся «обновлённым» без точки истории.

### Живой запуск

- Веб-сервер: `python manage.py runserver 0.0.0.0:8321` —
  **http://127.0.0.1:8321/**, страница истории:
  **http://127.0.0.1:8321/&lt;id&gt;/history** (маршрут — без префикса
  `share`; проверено HTTP: 200 с данными и пустой историей, неверный
  период → 400, отсутствующий инструмент → 404, бейдж demo, таблица
  наблюдений, график, «Изменение (процент)»).
- Демо-проверка автоматического накопления (без токена и Redis):
  создана демо-акция через авторизованный API, запущен
  `collect_prices --source demo --interval 2 --max-cycles 3`; в БД
  накоплены наблюдения с источником `demo`, distinct `quote_time`, процесс
  завершён штатно по лимиту циклов.
- Источник данных на страницах честно помечен: demo — «демонстрационные
  данные»; текущая цена — с явным происхождением
  (`last_price_source`: tinkoff / demo / manual / источник неизвестен);
  без токена в режиме tinkoff — честный статус недоступности.
- Повторная живая проверка финального кода выполнена на **отдельной
  временной SQLite** (абсолютный `DATABASES[default][NAME]`, проверен
  до первого SQL; рабочая БД не задействована): настоящий HTTP-сервер
  `runserver` на временной БД показал — ручная цена из HTML не может
  стать tinkoff/demo (spoof-поле игнорируется, изменённая цена → manual),
  переименование без изменения цены сохраняет источник, очистка цены
  снимает источник, нулевая цена отображается с пометкой; ограниченный
  demo-сбор `--max-cycles 3` обновил кеш и наблюдения согласованно,
  страница истории — серии с демо-бейджем и графиком из БД, неверный
  период → 400. Все проверочные процессы остановлены.

### Исправления по независимой проверке (все подтверждены тестами)

1. **Серии по (источник, валюта)**: `history_series` разделяет
   несопоставимые наблюдения — demo/рынок и разные валюты не смешиваются
   в одну линию и в один расчёт (регрессия: USD/tinkoff + RUB/demo
   больше не дают фиктивные +10/+10%). Период ограничен сверху текущим
   временем — точка с `quote_time` «завтра» не входит ни в один период
   (регрессия).
2. **Точность цены на SQLite**: поле цены `PriceObservation` переведено
   с NUMERIC-представления на текст десятичного числа (миграция 0009,
   данные перенесены). Полный roundtrip Decimal→БД→.Decimal проверен
   тестом на значениях, которые раньше молча округлялись
   (`1234567.123456789`, `12345678901.123456789`). Точность ранее
   сохранённых записей не заявляется восстановленной: если запись была
   округлена до миграции, исходное значение неизвестно — она переносится
   как есть.
3. **Происхождение текущей цены**: `Share.last_price_source`
   (tinkoff)/(demo)/(manual)/(NULL — неизвестно); демо-режим не выдаёт
   синтетику за рынок — происхождение видно в списке, на карточке и в
   API. Задача Celery и локальный `collect_prices` используют общий путь
   `apply_prices`: текущий кеш и наблюдения обновляются так же согласованно
   на обоих путях (наблюдения → история), ручная цена отмечается как
   ручная (регрессии обоих путей + переключения источника).
4. **Идентичность инструмента с историей**: figi/uid/ticker (и валюта)
   акции с накопленной историей не меняются через API (400), HTML-формы
   (ошибка формы), admin и импорт `add_shares` (пропуск с журналированием);
   обычное переименование работает (регрессии).
5. **Документация**: README дополнен `collect_prices`,
   `PRICE_SOURCE`/`PRICE_COLLECT_INTERVAL`, запуском истории
   (`<id>/history`); фактические числа и маршруты отражены здесь (в этом
   разделе), §5/§8 без изменений.

### Непроверенное / ограничения

- Живая интеграция с Tinkoff API (токен/сеть) не проверялась: наблюдения
  от реального источника не создавались; путь проверен тестами через
  подмену транспорта и локальное demo.
- Celery-запись не проверена живым beat/worker (Redis отсутствует) —
  только юнит-тесты общего пути записи.
- Точные цены на PostgreSQL не проверялись (SQLite-путь): на PostgreSQL
  NUMERIC-колонка хранится точно, миграция переносит данные без изменений.
- Производительность на больших объёмах не измерялась (индекс
  `(share, quote_time)` создан).
- Заявленная поддержка только Python 3.12.15 (как и прежде).
