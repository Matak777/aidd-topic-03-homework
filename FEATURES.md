# FEATURES.md — задание №4: новая функциональность

Документ формулирует функциональные требования к четырём группам из
HOMEWORK.md (задание №4), критерии приёмки, изменения модели данных и план
интеграции. Реализация идёт по этапам: после каждого этапа приложение
остаётся работоспособным. Текущий статус реализации указан в §5.

Общие принципы, действующие для всех групп:

- Все сделки — **исключительно виртуальные**: реальные ордера не отправляются
  ни при каких настройках (SDK-клиенты ордеров не вызываются).
- Живой Tinkoff API и Redis недоступны в среде. Подменённые данные не
  выдаются за живые котировки: любая недоступность интеграции показывается
  пользователю честно; для воспроизводимой демонстрации существует
  **явно включаемый** demo-режим с пометкой источника данных в БД и в
  интерфейсе.
- Цены внутри доменной логики хранятся и вычисляются точно (`Decimal` через
  exact-преобразование units/nano из gRPC `Quotation`); `Float` остаётся
  только в существующих полях `Share.last_price` (совместимость).

## 1. Группа 1: персональный мониторинг акций (этап 3, HOMEWORK.md)

### Понятные пользователю условия (политика событий)

Правило мониторинга — индивидуальное: инструмент + направление («цена ≥
порога» или «цена ≤ порога») + положительный порог (точное десятичное
число) + источник оценки (tinkoff/demo) + валюта + включено/отключено.
Оба направления одновременно поддерживаются отдельными правилами по
одному инструменту.

Совместимое наблюдение: тот же инструмент; источник совпадает точно;
валюта — без регистра (USD/usd — одна валюта); цена — точный Decimal из
наблюдения (`price_decimal`), не Float-кеш и не цена виртуальной сделки;
время котировки не позже момента проверки. Равенство порогу удовлетворяет
условию. Чужой источник/валюта, некорректная (нечисловая/неконечная) цена
и точка со временем позже момента проверки состояние правила не меняют.

Срабатывание, повторное взведение и изменение правил:

- при создании правила старая история НЕ проигрывается: старая последняя
  цена, даже уже подходящая, не уведомляет; первое НОВОЕ совместимое
  наблюдение, удовлетворяющее условию, создаёт уведомление; если данных
  ещё нет — ждём первое новое наблюдение;
- пока условие остаётся выполненным, новые подходящие цены повторов не
  создают; наблюдение вне условия повторно взводит правило; следующий
  вход в условие создаёт новое событие;
- при редактировании или включении правила актуальная совместимая
  небудущая цена становится исходным состоянием БЕЗ уведомления: если
  условие уже выполнено — перед новым срабатыванием нужен выход (наблю-
  дение вне условия), если данных нет — ждём первое новое наблюдение;
  отключённое правило не уведомляет;
- обработка ведёт по последовательности новых наблюдений (не только по
  последней цене) в устойчивом порядке по времени котировки и
  идентификатору; запоздавшая точка (время котировки раньше уже
  применённого состояния) не откатывает состояние и не создаёт
  ретроспективного события; повторная проверка, повторная доставка и
  перезапуск процесса не дублируют событие.

Уведомления внутри приложения (внешние рассылки не предусмотрены):
сохраняют снимок — инструмент (figi/тикер/название/валюта), цену,
порог, направление, источник, валюту, время котировки; изменение или
удаление правила не переписывает доставленное уведомление. Список
уведомлений с отметкой о прочтении; правило источник demo помечено
DEMO-бейджем и уведомления demo — тоже (не выдаются за живые).

Состояние и защита от повторов хранятся в БД. Создание уведомления и
переход состояния атомарны (одна транзакция), включая параллельных
обработчиков: дубли исключаются уникальной парой «правило+наблюдение» —
она допускает повторное событие после выхода/входа (это всегда другое
наблюдение). Ограничение SQLite: параллельная запись сериализуется
движком, транзакция используется с блокировкой строки правила; два
обработчика одной и той же пары разведены этим ограничением.

Владелец проверяется на сервере для всех списков, правил и уведомлений
(чужой известный ID → 404, аноним → redirect); изменения — только POST
с CSRF; чтение данные не меняет.

### Критерии приёмки (проверяются тестами)

1. Список, правила и уведомления видны и изменяемы только владельцем;
   чужие ID → 404 без изменений; POST без CSRF → 403.
2. Повторное добавление той же акции в тот же список — понятная ошибка
   (без дубля и без 500); то же имя списка у другого владельца допустимо.
3. Оба направления работают; равенство порогу удовлетворяет условию
   (тесты ≥, ≤ и «равно»).
4. Первое срабатывание — только на новое наблюдение (старая история не
   уведомляет, backlog не проигрывается).
5. Пока условие выполнено — повторов нет; выход повторно взводит;
   следующий вход — новое событие (повтор после выхода/входа возможен,
   уникальность только по направлению/порогу не запрещает его).
6. Редактирование/включение перестраивают исходное состояние без
   уведомления; отключённое правило не уведомляет.
7. Обработка последовательности наблюдений: порядок (время, id),
   повторный запуск проверки не дублирует; запоздавшая точка не
   откатывает состояние.
8. Чужой источник/валюта (в т.ч. usd/USD — одна валюта), будущая точка
   не меняют состояние правила.
9. Точность Decimal сохраняется после записи/чтения SQLite (порог,
   цена, снимок уведомления).
10. Оба пути интеграции (локальный коллектор и задача Celery) работают
    без Redis через общий путь записи наблюдений; сбой обработки
    правила не прерывает остальной цикл.
11. Удаление акции не даёт 500 в существующих HTML/API, не уничтожает
    историю портфелей; сработавшие уведомления переживают удаление
    правила и инструмента (снимки).

### Изменения модели данных

- `Watchlist`: владелец, название, `created_at`; уникальность
  `(user, name)` — то же имя у другого владельца допустимо.
- `WatchlistItem`: `watchlist` (CASCADE), `share` (CASCADE), `created_at`;
  уникальность `(watchlist, share)` — добавления без дублей.
- `WatchRule`: `user` (CASCADE), `share` (CASCADE), `direction`
  (`>=`/`<=`), `threshold` (ExactAmountField — точный текст Decimal,
  строго > 0), `source` (tinkoff/demo), `currency` (нормализуется в
  верхний регистр), `enabled`, `state` (`armed` — ожидает события /
  `triggered` — условие сейчас считается выполненным), `cursor_id`
  (высший обработанный id наблюдения по инструменту), `head_quote_time`
  (время последнего применённого состояния — отсекает запоздавшие
  точки), `created_at`/`updated_at`.
- `WatchEvent` (уведомление): `user` (CASCADE), `watch_rule` (SET_NULL —
  удаление правила не удаляет событие), `observation` (SET_NULL),
  снимки (`figi`, `ticker`, `share_name`, `share_currency`, `direction`,
  `threshold`, `source`, `currency`, `observed_price`, `quote_time`),
  `message`, `detected_at`, `is_read`/`read_at`; уникальность
  `(watch_rule, observation)` — дубли события исключены, повторы после
  выхода/входа (другое наблюдение) не запрещены.

### План интеграции

1. Модели + миграция (существующие таблицы не перестраиваются).
2. Сервис `watch_monitor`: совместимость и стабильный порядок обработки,
   пересчёт базового состояния (`reset_baseline`) при создании/
   редактировании/включении, атомарная обработка окна наблюдений
   (`process_rule`/`process_share`), создание уведомления со снимком.
3. Подключение к общему пути записи наблюдений `apply_prices` —
   локальный коллектор `collect_prices` и задача Celery
   `update_last_price` вызывают мониторинг автоматически; сбой обработки
   правила журнализуется, цикл продолжается (без обязательного Redis).
4. Views/формы/шаблоны/маршруты: списки (создание, карточка с
   добавлением/удалением инструментов), правила (создание, редактирование,
   вкл/откл, удаление), уведомления (список, отметка о прочтении);
   владелец — на сервере, изменения — POST с CSRF.
5. Общий валидатор/политика точности этапа 2 переиспользуется
   (`validate_metric`/`canonical_amount`); сервис выделяется так, чтобы
   будущие стратегии (этап 4) применяли те же условия — сами стратегии
   в этом этапе не реализуются.

### Маршруты и команды (факт)

Маршруты `dashboard/urls.py` (все под префиксом `/watch/…`):

- `watch/lists` — список наблюдения пользователя, POST создание;

`update_last_price` (опционально, без обязательного Redis) дают
одинаковое поведение.

## 2. Группа 2: виртуальный инвестиционный портфель

> Уточнённые требования этапа 2 (согласованы перед реализацией). Это
> требования к новой функциональности, а не описание готового результата.

### Требования

- **F2.1 Портфели.** Аутентифицированный пользователь создаёт именованные
  виртуальные портфели (несколько на пользователя). Состав портфеля:
  валюта (одна на портфель), источник оценки (`demo`/`tinkoff`, явно
  выбирается), положительный стартовый виртуальный денежный баланс.
- **F2.2 Сделки.** В портфеле регистрируются виртуальные покупки/продажи
  акций каталога: сторона BUY/SELL, количество (> 0), цена исполнения,
  неотрицательная комиссия, валюта и время. Реальные ордера не отправляются
  ни при каких настройках. Цена, введённая пользователем, — ручная цена
  виртуальной сделки; рыночные наблюдения она не подменяет. Цена,
  подставляемая формой по умолчанию, берётся только из подходящего
  сохранённого наблюдения (источник оценки, валюта инструмента, котировка
  не в будущем) и сопровождается показом источника и времени котировки.
- **F2.3 Учёт.** Покупка расходует «количество × цена + комиссию»;
  продажа возвращает «количество × цена − комиссию».
  Средневзвешенная себестоимость включает комиссию покупки; продажа
  уменьшает количество и не меняет среднюю себестоимость остатка, её
  комиссия уменьшает реализованную прибыль. После полного закрытия позиции
  фиктивной позиции/себестоимости не остаётся; следующая покупка начинает
  новый расчёт с нуля.
- **F2.4 Отказы без частичных изменений** (валидация до записи): недостаток
  денег, продажа сверх остатка, отрицательный денежный остаток, несовместимая
  валюта инструмента и портфеля, нечисловые/неконечные/недопустимо
  отрицательные величины, время операции в будущем или раньше последней
  операции портфеля (UTC; наивное время трактуется как UTC).
- **F2.5 Точность.** Все деньги/количества — Decimal; сохранение в SQLite
  честно точное (текст десятичного числа, как и цены наблюдений; NUMERIC/
  float-хранение молча округляет). Политика округления: в журнале
  сохраняются введённые значения без изменения; агрегаты (себестоимость,
  P/L, итоги) вычисляются в контексте 50 значащих цифр и округляются
  явно только для отображения (до 4 знаков после запятой). Переполнение,
  NaN, бесконечность (ввод и результаты) отклоняются.
- **F2.6 Оценка.** Открытые позиции оцениваются последним подходящим
  наблюдением выбранного источника и валюты инструмента (USD/usd — одна
  валюта; валюты не смешиваются), с `quote_time <= времени оценки` и
  устойчивым выбором при равных временах (quote_time, received_at, id).
  Показываются источник и время котировки. Отсутствующая котировка не
  подменяется другим источником, ручным кешем или ценой сделки; при
  неизвестной оценке хотя бы одной позиции итоги помечаются
  «неполная оценка» с показом известных составляющих. Закрытым позициям
  котировка не нужна. DEMO-оценка явно помечена во всех соответствующих
  итогах.
- **F2.7 Журнал.** Постоянный снимок исполнения и идентичности инструмента
  (figi/тикер/название/валюта) в самой операции; журнал — источник истины.
  Операции не редактируются и не удаляются через доступные интерфейсы;
  ссылки не теряют историю: `Trade.portfolio` — PROTECT (удаление
  портфеля с операциями отказывается понятным сообщением), `Trade.share` —
  SET_NULL при удалении акции (снимок сохраняется).
- **F2.8 Идемпотентность и атомарность.** У операции — ключ
  идемпотентности: повторная отправка того же ключа с теми же данными не
  создаёт дубль (возвращается существующая операция), того же ключа
  с другими данными — явный отказ. Проверка денег/остатка и запись
  операции атомарны; защита от параллельных операций — CAS-обновление
  cash (старое точное значение cash в WHERE) + полный откат при любом
  отказе. SQLite — одиночный писатель: второй параллельный writer либо не
  проходит CAS (данные изменились), либо получает ошибку занятости БД без
  частичных изменений (документируемое ограничение платформы).
- **F2.9 Доступ.** Все страницы и действия — только владельца, проверка
  на сервере (чужой известный ID → 404, подмена портфеля в форме → 404);
  изменения только POST с CSRF.
- **F2.10 Реиспользование.** Общий сервис исполнения операций отделён от
  представлений и пригоден для будущих виртуальных стратегий; сами
  стратегии на этом этапе не создаются.

### Критерии приёмки

1. Контрольный пример (тест): старт 1000; BUY 2×100 комиссия 2; BUY 3×120
   комиссия 3; SELL 2×130 комиссия 2 → остаток 3 единицы, средняя
   себестоимость 113, cash 693, реализованная прибыль 32; при котировке
   125 нереализованная прибыль 36, совокупный результат 68, полная оценка
   портфеля 1068, доходность 6.8%.
2. Две покупки 10×100 и 10×110 → 20 шт, средняя 105.0 (тест).
3. Продажа части позиции уменьшает количество, не меняет среднюю цену,
   увеличивает реализованный P/L (тест).
4. Продажа больше количества позиции запрещена (тест); недостаток средств
   отклоняется без изменения cash (тест); несовместимая валюта
   отклоняется (тест).
5. Полное закрытие: позиция исчезает, себестоимость и нереализованный
   P/L не остаются «хвостовыми»; новая покупка начинает новый расчёт
   (тест).
6. Точный roundtrip SQLite для денег/количеств с большим числом значащих
   цифр, включая накопленные итоги cash (тест).
7. Идемпотентность: тот же ключ → одна запись и тот же cash; тот же ключ
   с другими данными → отказ (тест).
8. Атомарный отказ: сбой записи операции не оставляет списанных денег
   (тест).
9. Портфель/журнал видны только владельцу; аноним → вход; POST-форма
   без CSRF → отказ (тесты).
10. Удаление акции не уничтожает операции (SET_NULL + снимок); удаление
    портфеля с операциями отказывается без 500 (тесты).
11. Отсутствующая подходящая котировка → позиция «без оценки», итоги
    помечены неполными, известные части видны (тест).
12. Журнал с пагинацией; одинаковые времена — устойчивый порядок (тест).

### Ревизия этапа 2: исправления дефектов и повторная живая проверка

Независимая ревизия выявила 7 дефектов; каждый исправлен с
регрессионными тестами (+15 тестов) и подтверждён повторным
настоящим HTTP-прогоном на отдельной временной SQLite (ENGINE/NAME —
assert-до первого SQL; рабочая БД не задействована):

1. **Идемпотентный повтор после новых операций**: идемпотентность
   проверяется ДО chronology — точный повтор старой операции при
   том же ключе возвращает прежнюю запись (302) без записи дубля и
   без изменения cash (`693` не изменился), даже после последующих
   операций; новый ключ задним числом → отказ («не раньше последней»),
   тот же ключ с другими данными → отказ.
2. **Ведущие нули в стартовом балансе**: форма канонизирует
   `initial_cash` до записи (`001000` → `1000`), созданный портфель
   допускает первую покупку (cash `693` в контрольном прогоне);
   CAS сравнивается с фактическим текстом БД — уже сохранённые
   неканонические корректные записи работают.
3. **Точность**: сделка, результат которой не сохраняется точно в
   заявленном диапазоне (10^-24 × 10^-24 ранее давала молчаливо
   бесплатную покупку), отклоняется ДО записи — cash и журнал не
   меняются (регрессия: отказ + неизменный cash); дельта 10^-8
   сохраняется точно (`999.99999999`); стоимость позиции
   `12345678901234567890123456789 × 1234567890.123456789` =
   `15241578753238836750342935775019051998.750190521` — ровно
   (эталонная сверка в независимом контексте теста).
4. **Текущая стоимость позиции** = количество × котировка
   (3 × 125 → `375.0000` в HTML; колонка больше не повторяет
   котировку).
5. **Честные итоги при неполной оценке**: без подходящей котировки
   полная оценка портфеля — «— (неполная оценка)» (не выглядит
   числом), совокупный P/L и доходность — неизвестны; cash
   (`700.0000`) и оценённые части показываются отдельно; позиция —
   «без оценки»; пустой портфель полностью оцениваем по cash.
6. **Повтор названия портфеля** (у того же владельца): понятная
   ошибка формы (200, «таким названием»), без 500 и без записи;
   то же имя у другого владельца допустимо (302).
7. **Источник на ошибочной форме**: повтор формы операции сохраняет
   фактический источник портфеля — tinkoff-портфель на ошибочном
   POST не получает DEMO-бейджа (проверено HTML: 0 вхождений DEMO).

Регресс истории цен пройден в том же прогоне: `/1/history` → 200,
стартовая страница → 200. Все проверочные процессы остановлены,
временные артефакты удалены. Живая интеграция Tinkoff, Redis и
PostgreSQL в этом прогоне по-прежнему не задействовались и не
заявляются проверенными.

### Вторая ревизия этапа 2: три дефекта и повторная живая проверка

Вторая независимая ревизия выявила 3 дефекта (+10 регрессионных
тестов, суммарно 188); каждый исправлен и подтверждён настоящим
HTTP-прогоном на отдельной временной SQLite (ENGINE/NAME — assert-до
первого SQL; рабочая БД не задействована):

1. **Средняя себестоимость падала decimal.Inexact**: контекст
   производных величин наследовал trap Inexact от точного контекста
   исполнения — после BUY 3×100+1 (средняя 301/3 требует округления)
   следующая BUY 1×1+0 падала (HTTP-ошибка). Политики разделены:
   контекст производных явно задаёт prec=120, округление
   ROUND_HALF_EVEN и отключённые traps (не наследует от вызывающего);
   дельта cash остаётся в точном контексте с контролем потерь.
   Проверено живым HTTP и тестами: последовательность BUY 3×100+1 →
   BUY 1×1+0 завершается — 2 операции, cash=698 (точный), количество
   4, средняя 75.5000 (с комиссией первой покупки), стоимость 302;
   частичная продажа (2×130−2 → cash 956, реализованный P/L 107),
   полная продажа (→ cash 1115, avg сброшен) и новая покупка
   (5×50+2 → cash 863, новая средняя 50.4000) работают.
2. **Хвостовые нули давали ложный отказ**: cash 999.000…0 (36
   хвостов) считался «не представимым». Канонизация снимает ТОЛЬКО
   незначащие нули точными строковыми операциями, независимо от
   Decimal-контекста (округляющий normalize() в контексте 28 не
   используется — он изменил бы большие точные значения; регрессия:
   `canonical_text_for_stored(123456789012345678901234567890.1)`
   сохраняет текст ровно). Проверено живым HTTP и тестами: BUY
   quantity='1.000000000000000000' × price='1.000000000000000000'
   проходит — cash=999, журнал хранит '1'; повтор той же операции
   (и после чтения портфеля из БД, и с вводом без хвостовых нулей) —
   идемпотентен: прежняя запись, без дубля, cash не изменился.
3. **Предел 18 дробных знаков проверялся не везде**: BUY
   quantity=10^-20 × price=10^20 записывался; форма принимала
   initial_cash=10^-24. Валидация `validate_metric` теперь проверяет
   заявленную точность (после снятия хвостовых нулей — не более 30
   целых и 18 значащих дробных цифр) на quantity/price/commission/
   initial_cash и в формах, и в сервисе, а также для сохраняемого
   результата cash; записи в журнал — канонические тексты.
   Проверено живым HTTP и тестами: quantity=10^-20 отклоняется до
   записи (200 с «вне заявленной точности хранения», cash и журнал
   не изменились; форма начального баланса отклоняет 10^-24 —
   портфель не создаётся). Хвостовые нули не отклоняются (см. п.2).
   Результат cash по-прежнему проверяется на представимость ДО
   записи (999.000…0 → '999').

Сопутствующие правки: `AmountField`/`ExactAmountField` max_length
48 → 49 (30 int + '.' + 18 frac; миграция 0011, данные не меняются);
view формы операции дополнительно переводит Decimal-исключения
арифметики в понятный отказ формы, не 500. Регрессии в том же
прогоне: `/1/history` → 200, `/` → 200. Все проверочные процессы
остановлены, временные артефакты удалены; Tinkoff/Redis/PostgreSQL
по-прежнему не задействовались и не заявляются проверенными.

### Сопутствующая правка подписи коллектора (история цен)

`collect_cycle` возвращает число реально обработанных акций, а
management-команда подписывает его как «число записанных наблюдений» —
повторная доставка, не создавшая строку, не должна заявляться новой
записью. Подпись/счётчик делаются точными («акций обработано N, новых
наблюдений M»); дедупликация и принятая история сохраняются, это
сопутствующее уточнение сообщения, а не переделка функциональности.

## 3. Группа 3: история изменения рыночных цен (этап 1 — реализуется сейчас)

### Требования

- **F3.1 Накопление.** Рыночные цены всех акций каталога автоматически
  сохраняются в БД: точная цена (Decimal из units/nano), инструмент,
  валюта, время котировки и время получения, источник данных.
- **F3.2 Дедупликация доставки.** Повторная доставка одного наблюдения не
  создаёт дубликат; одинаковая цена в разное время сохраняется как разные
  наблюдения.
- **F3.3 Периодический сбор без Redis.** Локальный управляемый процесс
  (management command) с настраиваемым интервалом, обработкой ошибок и
  штатной остановкой; собирает цены через те же сервисы SDK, что и
  существующая задача Celery (обязательность Redis сохраняется
  опциональной).
- **F3.4 Просмотр истории.** Доступная из интерфейса страница истории
  акции: выбор периода, список наблюдений, абсолютное и процентное
  изменение, график из накопленных данных.
- **F3.5 Демонстрационный источник.** Явно включаемый demo-режим
  (без токена): синтетические цены, помеченные источником `demo`, и
  пометка «демонстрационные данные» в интерфейсе. Обычный режим без токена
  честно показывает недоступность интеграции.

### Критерии приёмки

1. Точность: Quotation(units=123, nano=450000000) → Decimal("123.45")
   (тест; никакой float-арифметики при записи).
2. Повторная доставка: два наблюдения на один (share, quote_time, source)
   → одна строка (тест с двойным сохранением).
3. Одинаковая цена в разное время → две строки (тест).
4. `quote_time` и `received_at` — разные поля; получатель не переписывает
   время котировки (тест).
5. Коллектор: 3 цикла с --max-cycles создают накопление, интервал/очередь
   обрабатывают сбой источника без падения процесса (тест).
6. Страница истории: пустая история/одна точка/нулевая начальная цена/
   неверный период/отсутствующий инструмент — явные состояния без 500
   (тесты на все).
7. График строится из БД (без внешних RPC) при ≥2 точках; для 0/1 точек —
   явное сообщение.
8. Demo-режим включается только явной настройкой; источник отмечается в БД
   и заметен пользователю (тест + интерфейс).

### Изменения модели данных (этап 1 — сделано)

- `PriceObservation`:
  - `share` (FK Share, CASCADE, related_name="price_observations"),
  - `price` (CharField(40) — точная цена как текст десятичного числа;
    NUMERIC-представление на SQLite молча округляло, текст даёт точный
    roundtrip; миграция 0009 перенесла данные),
  - `currency` (CharField(20) — валюта наблюдения),
  - `source` (CharField(20), choices tinkoff/demo — происхождение),
  - `quote_time` (DateTimeField — время котировки от источника),
  - `received_at` (DateTimeField(auto_now_add=true) — время получения).
  - Уникальность `(share, source, quote_time)` — ключ дедупликации
    доставки: повторная доставка того же наблюдения (тот же источник и
    то же время котировки) не создаёт вторую строку; get_or_create —
    идемпотентно (первая копия выигрывает). Одна и та же цена в другое
    время — другая строка (другой quote_time).
  - Индекс `(share, quote_time)` для выборок по периоду.
- `Share` (дополнения этапа 1): `last_price_source` (CharField(20)
  null — tinkoff/demo/manual; NULL — происхождение неизвестно, честно
  показывается пользователю).

### План интеграции (этап 1 — сделано)

- `services/price_history.py`: `quotation_to_decimal` (exact units/nano),
  `record_observations` (дедуплицированная запись), провайдеры цен
  (`tinkoff` — через существующий `get_last_prices` с RPC-дедлайном,
  `demo` — детерминированный синтетический генератор), `collect_cycle`
  (один цикл сбора), расчёты истории и график из БД.
- `manage.py collect_prices --interval N --source tinkoff|demo --max-cycles N`
  — локальный периодический сбор; ошибки цикла технологуются и цикл
  продолжается; `KeyboardInterrupt`/`SIGTERM` — штатная остановка.
- Celery сохранён: задача `update_last_price` дополнительно пишет
  наблюдения (этот же источник данных).
- Страница `<id>/history?period=...` (dashboard.urls смонтированы в корне
  config.urls — префикса `share/` нет) + ссылки с карточки и списка;
  настройка `PRICE_SOURCE` (tinkoff|demo) и `PRICE_COLLECT_INTERVAL`.

## 4. Группа 4: симулятор инвестиционных стратегий

### Требования

- **F4.1 Стратегии.** Аутентифицированный пользователь создаёт именованную
  стратегию (несколько на пользователя): инструмент, тип условия
  («цена ≥ X», «цена ≤ X», «изменение за период ≥ Y%»), действие (виртуальная
  покупка/продажа заданного количества), целевой портфель (группа 2).
- **F4.2 Автосделки.** При выполнении условия стратегия автоматически
  создаёт виртуальную сделку в привязанном портфеле. Условие выполняется
  один раз (не генерирует сделки на каждом цикле), для повторного срабатывания
  стратегия должна быть отредактирована/перевзведена.
- **F4.3 Журнал.** Каждое срабатывание записывается в журнал стратегии:
  время, условие, снимок цены, созданная сделка.
- **F4.4 Оценка.** Для стратегии показывается суммарная эффективность:
  виртуальные сделки → позиция/закрытый P/L по данным портфеля +
  текущие цены из БД наблюдений. Требование наблюдений — к группе 3.
- **F4.5 Управление.** Стратегию можно включать/выключать; выключенная не
  срабатывает.

### Критерии приёмки

1. Условие «цена ≥ X» на наблюдении цены ≥ X срабатывает ровно один раз
   на данный ключ условия (тест с двумя последовательными проверками).
2. Выключенная стратегия не срабатывает (тест).
3. Сделка создаётся виртуально: только в портфеле, никаких обращений к
   ордерам SDK (тест: mock SDK-ордера отсутствует).
4. Некорректная стратегия (отрицательное количество/неизвестное условие)
   не создаётся (валидация).
5. Эффективность считается из виртуальных сделок и наблюдений; при пустой
   истории — заглушка.

### Изменения модели данных

- `Strategy`: `user` (FK), `name`, `share` (FK PROTECT), `condition_type`
  (price_above/price_below/price_change_pct), `condition_value` (Decimal),
  `action` (buy/sell), `quantity` (Decimal > 0), `portfolio` (FK Portfolio,
  null — если группа 2 ещё не наполнена), `enabled` (bool),
  `max_executions` (int, по умолчанию 1), `created_at`.
- `StrategyExecution`: `strategy` (FK CASCADE), `condition_key`
  (CharField), `triggered_price` (Decimal), `quote_time`, `trade` (FK Trade,
  null, SET_NULL), `executed_at` (auto_now_add); уникальность
  `(strategy, condition_key)` — защита от повторного срабатывания
  того же условия; ключевая величина события — «условие + целевой уровень».

### План интеграции

1. Модели Strategy/StrategyExecution + миграция (после этапа 2).
2. Сервис `run_strategies()`: читает последние наблюдения из БД, для всех
   активных стратегий проверяет условия и создаёт исполнения (и сделки);
   идемпотентность — уникальность «сигнатуры».
3. Точка вызова — тот же локальный коллектор (опция `--run-strategies`)
   и/или Celery beat; внешние RPC не нужны.
4. Views: формы настроек стратегии, страницы журнала и эффективности;
   ссылка из портфеля.

### Уточнения после повторной независимой проверки (подтверждены тестами и HTTP)

- Источник ручной цены в HTML определяет сервер: `last_price_source`
  исключён из редактируемых полей формы/формы admin — из POST его
  подделать нельзя, изменённая цена (в т.ч. нулевая) всегда становится
  manual; переименование без изменения цены сохраняет прежний источник.
- Очистка цены снимает источник согласованно во всех путях (HTML, admin,
  API create/update): нет цены — нет источника.
- Нулевая цена имеет пометку источника (проверка значения, не истинности)
  на карточке и в списке.
- `apply_prices` записывает кеш/источник/тренд/время и наблюдение атомарно
  на инструмент (`transaction.atomic`): при сбое записи наблюдения кеш
  откатывается и не остаётся «обновлённым» без точки истории.

### Живой запуск

- Веб-сервер: `python manage.py runserver 0.0.0.0:8321` —
  **http://127.0.0.1:8321/**, страница истории:
  **http://127.0.0.1:8321/&lt;id&gt;/history** (маршрут — без префикса
  `share`; проверено HTTP: 200 с данными и пустой историей, неверный
  период → 400, отсутствующий инструмент → 404, бейдж demo, таблица
  наблюдений, график, «Изменение (процент)»).
- Демо-проверка автоматического накопления (без токена и Redis):
  создана демо-акция через авторизованный API, запущен
  `collect_prices --source demo --interval 2 --max-cycles 3`; в БД
  накоплены наблюдения с источником `demo`, distinct `quote_time`, процесс
  завершён штатно по лимиту циклов.
- Источник данных на страницах честно помечен: demo — «демонстрационные
  данные»; текущая цена — с явным происхождением
  (`last_price_source`: tinkoff / demo / manual / источник неизвестен);
  без токена в режиме tinkoff — честный статус недоступности.
- Повторная живая проверка финального кода выполнена на **отдельной
  временной SQLite** (абсолютный `DATABASES[default][NAME]`, проверен
  до первого SQL; рабочая БД не задействована): настоящий HTTP-сервер
  `runserver` на временной БД показал — ручная цена из HTML не может
  стать tinkoff/demo (spoof-поле игнорируется, изменённая цена → manual),
  переименование без изменения цены сохраняет источник, очистка цены
  снимает источник, нулевая цена отображается с пометкой; ограниченный
  demo-сбор `--max-cycles 3` обновил кеш и наблюдения согласованно,
  страница истории — серии с демо-бейджем и графиком из БД, неверный
  период → 400. Все проверочные процессы остановлены.

### Исправления по независимой проверке (все подтверждены тестами)

1. **Серии по (источник, валюта)**: `history_series` разделяет
   несопоставимые наблюдения — demo/рынок и разные валюты не смешиваются
   в одну линию и в один расчёт (регрессия: USD/tinkoff + RUB/demo
   больше не дают фиктивные +10/+10%). Период ограничен сверху текущим
   временем — точка с `quote_time` «завтра» не входит ни в один период
   (регрессия).
2. **Точность цены на SQLite**: поле цены `PriceObservation` переведено
   с NUMERIC-представления на текст десятичного числа (миграция 0009,
   данные перенесены). Полный roundtrip Decimal→БД→.Decimal проверен
   тестом на значениях, которые раньше молча округлялись
   (`1234567.123456789`, `12345678901.123456789`). Точность ранее
   сохранённых записей не заявляется восстановленной: если запись была
   округлена до миграции, исходное значение неизвестно — она переносится
   как есть.
3. **Происхождение текущей цены**: `Share.last_price_source`
   (tinkoff)/(demo)/(manual)/(NULL — неизвестно); демо-режим не выдаёт
   синтетику за рынок — происхождение видно в списке, на карточке и в
   API. Задача Celery и локальный `collect_prices` используют общий путь
   `apply_prices`: текущий кеш и наблюдения обновляются так же согласованно
   на обоих путях (наблюдения → история), ручная цена отмечается как
   ручная (регрессии обоих путей + переключения источника).
4. **Идентичность инструмента с историей**: figi/uid/ticker (и валюта)
   акции с накопленной историей не меняются через API (400), HTML-формы
   (ошибка формы), admin и импорт `add_shares` (пропуск с журналированием);
   обычное переименование работает (регрессии).
5. **Документация**: README дополнен `collect_prices`,
   `PRICE_SOURCE`/`PRICE_COLLECT_INTERVAL`, запуском истории
   (`<id>/history`); фактические числа и маршруты отражены здесь (в этом
   разделе), §5/§8 без изменений.

### Непроверенное / ограничения

- Живая интеграция с Tinkoff API (токен/сеть) не проверялась: наблюдения
  от реального источника не создавались; путь проверен тестами через
  подмену транспорта и локальное demo.
- Celery-запись не проверена живым beat/worker (Redis отсутствует) —
  только юнит-тесты общего пути записи.
- Точные цены на PostgreSQL не проверялись (SQLite-путь): на PostgreSQL
  NUMERIC-колонка хранится точно, миграция переносит данные без изменений.
- Производительность на больших объёмах не измерялась (индекс
  `(share, quote_time)` создан).
- Заявленная поддержка только Python 3.12.15 (как и прежде).
