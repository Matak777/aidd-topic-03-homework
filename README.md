# Investing Demo

Django-приложение для просмотра и управления списком акций, графиков котировок Tinkoff Invest и REST API.

## Требования

- Python 3.12 (локально проверена версия 3.12.15). Метаданные проекта допускают Python 3.12–3.14, но версии 3.13 и 3.14 в этой работе не проверялись.
- [uv](https://docs.astral.sh/uv/) для установки зафиксированных зависимостей.
- SQLite используется по умолчанию. PostgreSQL можно подключить настройками `.env`.
- Redis нужен только для запуска Celery worker и Beat. Django-сайт работает без Redis и Docker.
- Для запросов живых данных нужен действующий `TINKOFF_TOKEN`. Без него график показывает понятное сообщение, команда импорта и фоновое обновление явно сообщают об ошибке.

## Установка и локальный запуск без Docker

Установите Python 3.12+ и uv обычным для вашей системы способом. В корне репозитория создайте виртуальное окружение и установите версии из `uv.lock`:

```sh
uv venv --python 3.12
```

Активируйте окружение (или используйте путь к его `python` в команде `uv pip`):

```sh
# macOS / Linux
source .venv/bin/activate

# Windows PowerShell
.venv\Scripts\Activate.ps1
```

Установите приложение и зафиксированные зависимости:

```sh
uv sync --frozen
```

Tinkoff SDK входит в lock и устанавливается при каждой `uv sync`. В `vendor/tinkoff-investments` сохранён исходный код официального [репозитория SDK](https://github.com/Tinkoff/invest-python), upstream commit `1cc84950266d62cd0bc7a43ad764dddfd4252630`, лицензия Apache-2.0. Содержимое `tinkoff/` взято без изменений. Локальная упаковка удаляет upstream-зависимость `tinkoff>=0.1.1`, которую нельзя разрешить из доступного PyPI, и задаёт локальное описание/путь README; остальные runtime-зависимости сохранены с эквивалентными диапазонами версий. Источник, лицензия и изменения packaging metadata описаны в `vendor/tinkoff-investments/UPSTREAM.md`. Это исправление согласованности метаданных, а не утверждение о неработоспособности клиента.

Повторный `uv sync --frozen` сохраняет SDK, а `uv pip check` должен завершаться без несовместимостей.

Скопируйте пример окружения и при необходимости измените значения:

```sh
# macOS / Linux
cp .env.example .env

# Windows PowerShell
Copy-Item .env.example .env
```

В примере включена локальная SQLite; секрет Tinkoff не задан. Для локального запуска сайта не нужны ни Docker, ни PostgreSQL, ни Redis. Примените миграции и запустите сервер:

```sh
python manage.py migrate
python manage.py runserver
```

Откройте <http://127.0.0.1:8000/>. Создание администратора по желанию:

```sh
python manage.py createsuperuser
```

## Настройка

Настройки читаются из переменных окружения; `python-dotenv` автоматически загружает локальный `.env`, который исключён из Git.

| Переменная | Назначение |
| --- | --- |
| `DJANGO_DEBUG` | Режим отладки; по умолчанию `true` для локальной разработки. |
| `DJANGO_SECRET_KEY` | Секрет Django. Для `DJANGO_DEBUG=false` обязателен. |
| `DJANGO_ALLOWED_HOSTS` | Разделённый запятыми список хостов. |
| `DJANGO_CSRF_TRUSTED_ORIGINS` | Разделённый запятыми список доверенных HTTPS-источников. |
| `DB_ENGINE` | `sqlite` (по умолчанию) или `postgresql`. |
| `SQLITE_NAME` | Путь к SQLite-файлу; по умолчанию `db.sqlite3` в корне проекта. |
| `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_HOST`, `POSTGRES_PORT` | Подключение к PostgreSQL, если выбрано `DB_ENGINE=postgresql`. |
| `TINKOFF_TOKEN` | Токен Tinkoff Invest; без значения живые запросы не выполняются. |
| `TINKOFF_RPC_TIMEOUT_SECONDS` | Положительный конечный deadline для каждого синхронного unary gRPC-вызова; по умолчанию `10` секунд. |
| `PRICE_DATA_MODE` | `live` (по умолчанию) или явно включаемый `demo`; demo генерирует синтетические, не рыночные значения. |
| `PRICE_COLLECTION_INTERVAL_SECONDS` | Интервал стандартного локального сбора цен в секундах; по умолчанию `300`. |
| `CELERY_BROKER_URL` | URL Redis broker; используется только Celery. |
| `CELERY_TASK_ALWAYS_EAGER` | Выполнение Celery task синхронно, в основном для локальных тестов. |

Для production задайте непредсказуемый `DJANGO_SECRET_KEY`, `DJANGO_DEBUG=false`, корректные allowed hosts и PostgreSQL credentials. Не коммитьте `.env`.

## Загрузка акций и рыночные данные

После установки SDK и настройки `TINKOFF_TOKEN` загрузите справочник из Tinkoff Invest:

```sh
python manage.py add_shares
```

Сервис графика, обновление цены и импорт справочника используют Tinkoff API. Без токена или при ошибке провайдера приложение показывает/логирует ошибку, а не выдает демонстрационные данные за настоящие. На все синхронные unary RPC установлен конечный deadline, ограниченный `TINKOFF_RPC_TIMEOUT_SECONDS`; превышение срока отображается как понятная ошибка для цены, графика или импорта. В тестах транспорт и внешние ответы подменяются mock-объектами.

## История цен и локальный сбор

На странице списка акций и странице отдельной акции есть переход к истории. Экран истории показывает сохранённые наблюдения, источник, валюту, время котировки отдельно от времени получения, график и абсолютное/процентное изменение за выбранный период. Метрики считаются отдельно для каждой сопоставимой серии с одинаковыми источником и валютой; несопоставимые значения не вычитаются друг из друга. Доступные периоды: 24 часа, 7/30/90/365 дней и всё время. История накапливается при запуске фонового процесса; HTTP-запрос к экрану истории не обращается к Tinkoff и не подменяет пустые данные текущей котировкой.

Обычный режим — `PRICE_DATA_MODE=live`. С токеном локальный сбор получает котировки Tinkoff и сохраняет их. Без `TINKOFF_TOKEN` экран сообщает о недоступности живого источника, а команда сбора завершается понятной ошибкой вместо запуска бесполезного цикла.

Для воспроизводимой локальной демонстрации явно задайте в `.env`:

```dotenv
PRICE_DATA_MODE=demo
TINKOFF_TOKEN=
```

Демо-режим создаёт синтетические значения, помечает источник в БД и интерфейсе и не обращается к внешнему API. Эти значения не являются котировками и не записываются в кэш `Share.last_price`, который используется как последняя цена инструмента. Уже сохранённая подтверждённая live-цена остаётся без изменений.

Для кэша последней цены сохраняются источник и время котировки. В REST API присутствуют поля `last_price_source` и `last_price_observed_at`: источник `tinkoff` означает live-данные, `manual` — вручную введённое значение, `unknown` — старое значение без подтверждённого происхождения. В HTML старые цены с неизвестным источником помечаются как неподтверждённые; при ошибке Tinkoff последнее значение не перезаписывается. Изменение `last_price` через REST API, HTML-форму или Django admin маркирует значение как `manual`, не как рыночную котировку.

Изменение валюты или идентификатора инструмента (`FIGI`, `ISIN`, тикер, UID) сбрасывает кэш цены, источник, время и тренд. При наличии сохранённой истории изменение идентификатора отклоняется: создайте отдельный инструмент, чтобы прежние наблюдения не стали историей другого инструмента. Исторические цены и валюты не переписываются. Обновление названия само по себе не сбрасывает provenance. Импорт `add_shares` сопоставляет существующие инструменты только по FIGI/UID; неуникальный ISIN и изменяемый тикер не используются для слияния. Если FIGI и UID указывают на разные записи либо конфликтует уникальный идентификатор, импорт завершается понятной ошибкой целиком, без частичных изменений. Импорт применяет ту же защиту истории.

Цвет тренда в списке применяется только для live-цены Tinkoff: `true` подсвечивается зелёным, `false` — розовым, неизвестное направление (`None`, например первая котировка) — нейтрально. Значения manual и unknown остаются без трендовой подсветки.

История цен в Django admin доступна для чтения, но ручное добавление `PriceObservation` запрещено: записи создаёт collector.

Запустите сбор цен в отдельном терминале (интервал указывается в секундах; команда без `--max-cycles` работает до Ctrl+C/SIGTERM):

```sh
python manage.py collect_prices --interval 5
```

Для ограниченной проверки трёх циклов на одном инструменте:

```sh
python manage.py collect_prices --interval 1 --max-cycles 3 --share-id <ID_АКЦИИ>
```

Без `--share-id` каждый цикл обрабатывает весь каталог. Команда использует общий код обновления с Celery, но локально выполняется напрямую и не требует Redis. После Ctrl+C/SIGTERM новые инструменты не начинаются: текущий запрос может завершиться в пределах установленного RPC deadline, затем процесс восстанавливает обработчики сигналов и штатно выходит.

## Персональные списки и ценовые уведомления

После входа в приложение доступны «Мои списки» и «Уведомления» в верхней навигации:

- `/watchlists/` — создание личного списка;
- `/watchlists/<id>/` — добавление/удаление инструментов, создание/редактирование правил, включение/отключение и удаление правил, переименование/удаление списка;
- `/alerts/` — личный журнал уведомлений и отметка о прочтении.

Каждый инструмент может быть добавлен в список один раз. Для него можно настроить несколько правил цены с точным десятичным порогом, условием `>=` или `<=`, источником `tinkoff`/`demo` и валютой. Сопоставление кода валюты регистронезависимое (`USD` и `usd` обозначают одну валюту), но сохранённые значения не переписываются: уведомление сохраняет написание валюты из исходного наблюдения. Разные валюты и источники не смешиваются. Цена, порог, направление, source, валюта и время события сохраняются в уведомлении как неизменяемый снимок. Demo-источник явно помечается в списке правил и уведомлении; синтетические цены не являются рыночными данными.

Семантика создания отличается от редактирования/включения. При создании курсор ставится после последней существующей точки истории, старая история не проигрывается, а правило остаётся взведённым: первое последующее наблюдение, подходящее по условию, создаёт уведомление даже если старая цена уже была выше/ниже порога. При редактировании и повторном включении последнее сохранённое наблюдение задаёт baseline: если оно уже удовлетворяет условию, сперва нужен выход, после которого правило взводится. При отсутствии старой истории первое новое подходящее наблюдение сразу уведомляет. В любом случае повторов, пока условие непрерывно выполнено, нет; после выхода и нового входа создаётся новое уведомление. После остановки collector новые наблюдения обрабатываются при следующем цикле по времени события; более старое наблюдение, пришедшее после курсора, не откатывает состояние.

Удаление инструмента из HTML или REST API удаляет его рыночную историю и связанные элементы/правила. Уже созданные уведомления сохраняются для каждого владельца с полным снимком события; ссылки на удалённые правило и observation обнуляются, никакие уведомления других пользователей не удаляются.

Проверка владельца выполняется на сервере: чужие списки, правила и уведомления недоступны по известному ID. Все действия изменения интерфейса используют POST и CSRF. Это только внутриприкладные уведомления, без писем, push и внешних сообщений.

Обработчик запускается автоматически после каждого цикла существующего локального collector и после Celery-задачи обновления цен. Для работы без Redis запускайте веб-сайт и collector в отдельных терминалах:

```sh
python manage.py runserver
python manage.py collect_prices --interval 5
```

В локальной демонстрации установите `PRICE_DATA_MODE=demo` в `.env`; collector будет создавать явно маркированные синтетические наблюдения и соответствующие уведомления. Для Tinkoff нужен `PRICE_DATA_MODE=live` и действующий `TINKOFF_TOKEN`. Обработка уведомлений тестировалась на SQLite; `select_for_update` сериализует обработку правила в БД с поддержкой блокировок строк (например, PostgreSQL). SQLite не обеспечивает такую же сериализацию параллельных процессов; уникальные DB-ограничения и транзакции предотвращают повторное уведомление при повторной обработке, но конкурентную нагрузку на PostgreSQL в этой среде не проверяли.

## Celery и Redis (опционально)

Установите и запустите Redis отдельно от приложения. Затем в двух терминалах, с активированным `.venv`:

```sh
celery -A config worker -l info
```

```sh
celery -A config beat -l info
```

Celery Beat запускает обновление сохранённых цен каждые пять минут. Если Redis не запущен, worker/Beat не смогут подключиться к broker; веб-приложению для обычных HTTP-запросов Redis не нужен.

## REST API

Основной endpoint: <http://127.0.0.1:8000/api/v1/shares/>. Чтение доступно анонимно, изменения требуют аутентификации. Для фильтров доступны `name` и `ticker`, сортировки `name` и `ticker`, поиск по имени. Пагинация — limit/offset, размер страницы по умолчанию 100.

## Проверки

```sh
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py migrate
python manage.py test
uv pip check
```

Тесты используют SQLite и моки для Tinkoff API. Они проверяют локальную логику, но не подтверждают доступность Redis, Tinkoff API или достоверность живых котировок.
Проверки регистрации также передают нормализованные email/username валидаторам пароля до создания пользователя.

## Управление зависимостями

- `pyproject.toml` задаёт поддерживаемые диапазоны прямых зависимостей и локальный SDK package.
- `uv.lock` фиксирует версии и источники приложения и SDK для воспроизводимой установки командой `uv sync --frozen`; повторная синхронизация сохраняет SDK.
- `requirements.txt` экспортирован из lock-файла с версиями и hash и ссылается на vendored SDK по относительному пути `./vendor/tinkoff-investments`.
