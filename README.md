# investing (Investing Demo)

Учебный инвестиционный дашборд: каталог акций с HTML-интерфейсом и REST API,
фоновое обновление цен по расписанию (Celery beat), графики Plotly, загрузка
каталога из Tinkoff Invest API (gRPC).

Состав стека: Django 5.2 LTS, DRF 3.16, django-filter 25, Celery 5.6, Redis-клиент 6,
plotly 6, Tinkoff Invest SDK (вендорный, см. ниже). Проверено на Python 3.12.

> Современный SDK Tinkoff Invest (pip-пакеты `tinkoff-investments`/`tinkoff`)
> **удалён из PyPI**, официальный репозиторий заархивирован. Рабочая копия
> SDK сохранена в `vendor/tinkoff-investments` (источник, лицензия,
> происхождение и изменения описаны там же и в MODERNIZATION.md).

## Требования

- Python **3.12** (проверено на 3.12.15; поддержка 3.10–3.13 не проверялась —
  заявлять её не следует).
- [uv](https://docs.astral.sh/uv/) — для воспроизводимой установки. При желании
  можно установить зависимости из `requirements.txt` обычным pip.
- Redis — **только** для Celery beat/worker (фонового обновления цен).
  Без Redis сайт, API, графики и локальный сбор истории цен работают;
  попытка запустить beat/worker завершится явной ошибкой соединения.
- Docker/PostgreSQL — необязательны: по умолчанию используется SQLite.

## Установка

```bash
# 1) Создать окружение из lock-файла (нужен uv)
uv sync                      # создаст .venv и установит зависимости
# либо без uv: python3.12 -m venv .venv && .venv/bin/pip install -r requirements.txt

# 2) Настройки окружения
cp .env.example .env         # значение по умолчанию работоспособно
#   SECRET_KEY                — замените на свой секрет в production
#   TINKOFF_TOKEN             — токен Tinkoff Invest API (пусто = без рыночных данных)
#   PRICE_SOURCE              — tinkoff (умолчание) или demo (синтетические цены)
#   PRICE_COLLECT_INTERVAL    — интервал локального сборщика, сек (умолчание 10)
#   DATABASE=postgres + DB_*  — если хотите PostgreSQL вместо SQLite

# 3) Миграции
uv run python manage.py migrate        # или .venv/bin/python manage.py migrate

# 4) Запуск веб-приложения
uv run python manage.py runserver
#   http://127.0.0.1:8000/           — список акций
#   http://127.0.0.1:8000/api/v1/shares/ — REST API
#   http://127.0.0.1:8000/<id>/history   — история цен конкретной акции
```

## Что работает без внешних сервисов

- HTML-интерфейс: список/карточка акции, добавление, редактирование, удаление
  (аутентифицированным пользователем), пагинация, подсветка изменения цены.
- Регистрация и вход по email, выход.
- REST API `/api/v1/shares/`: CRUD, фильтры `?name=/?ticker=`, поиск `?search=`,
  сортировка `?ordering=name|ticker`, пагинация limit/offset.
- **История цен** (группа 3 задания №4): накопление наблюдений цен
  (модель `PriceObservation`: цена, валюта, источник, время котировки и
  получения), дедупликация повторяющихся наблюдений, страница
  `<id>/history` с периодами 1d/7d/30d/90d/all, абсолютными и процентными
  изменениями, списком наблюдений и графиком, построенным из накопленных
  данных (без внешних запросов). Серии наблюдений разделяются по источнику
  и валюте — несопоставимые значения (demo с рынком, разные валюты)
  не смешиваются в одну линию или изменения.
- **Виртуальные портфели** (группа 2 задания №4, этап 2): личные
  виртуальные портфели с журналом операций BUY/SELL (симуляция, ордера
  не отправляются ни при каких настройках). Страницы (только владелец,
  вход по email):
  - `/portfolios` — список портфелей;
  - `/portfolios/create` — создание (валюта, источник оценки
    demo/tinkoff, положительный стартовый баланс);
  - `/portfolios/<id>` — состав и итоги (cash, оценка позиций по
    последнему подходящему наблюдению выбранного источника,
    реализованный/нереализованный P/L, совокупный результат,
    доходность к старту);
  - `/portfolios/<id>/journal` — журнал операций (пагинация,
    источник истины; записи не редактируются и не удаляются);
  - `/portfolios/<id>/trades/new` — операция BUY/SELL (количество > 0,
    ручная цена исполнения > 0, комиссия >= 0, время UTC не в будущем
    и не раньше последней операции, ключ идемпотентности). Цена по
    умолчанию подставляется только из подходящего сохранённого
    наблюдения с показом его источника и времени.
- Учёт портфеля: покупка расходует `количество × цена + комиссию`,
  продажа возвращает `количество × цена − комиссию`; средневзвешенная
  себестоимость включает комиссию покупки; продажа не меняет среднюю
  себестоимость остатка; полное закрытие начинает новый расчёт.
- Точность (политика по итогам ревизий этапа 2): деньги/количества
  хранятся текстом Decimal (`ExactAmountField`, точный roundtrip при
  повторном чтении из SQLite) с допуском до 30 целых и до 18 ЗНАЧАЩИХ
  цифр в дробной — хвостовые нули не увеличивают требуемую точность;
  предел одинаково проверяется в формах (количество/цена/комиссия/
  стартовый баланс) и в сервисе, включая сохраняемый результат cash.
  В БД записывается канонический текст без ведущих нулей/экспоненты и
  без незначащих хвостовых нулей ('1.000000000000000000' → '1');
  канонизация — точные строковые операции, не зависит от
  Decimal-контекста (округляющий normalize() в контексте 28 не
  используется). Расчёты производных величин (позиции, средняя
  себестоимость, P/L, итоги) — Decimal с контекстом 120 значащих
  цифр и явно заданным правилом округления, без наследования trap'ов
  от вызывающего: умножения/суммы точны, деление округляется по
  объявленному правилу; денежная дельта cash вычисляется в отдельном
  контексте с контролем точности: если точный результат не сохраняется
  в заявленном диапазоне, операция отклоняется ДО записи без
  частичных изменений (молчаливо бесплатных сделок нет); агрегаты
  округляются явно только для отображения (4 знака);
  NaN/бесконечность/переполнение отклоняются.
- Отказы без частичных изменений: нехватка денег, продажа сверх
  остатка, несовместимая валюта, неверные величины/время — отклоняются;
  запись операции и cash атомарны (CAS по фактическому тексту cash
  в БД — неканонические, но корректные ранее сохранённые записи
  работают; полный откат при сбое); повторная отправка одной операции
  с тем же ключом возвращает прежнюю запись без изменений даже после
  последующих операций — в том числе с вводом, замаскированным
  хвостовыми нулями ('1.000000000000000000' и '1' — один и тот же
  payload); с другими данными — отказ; новая операция задним числом
  («раньше последней») — отказ.
- Честные итоги: при неполной оценке (у открытой позиции нет
  подходящей котировки выбранного источника) полная оценка портфеля
  показывается как «— (неполная оценка)», совокупный P/L и доходность —
  неизвестны; cash и оценённые позиции показываются отдельно; пустой
  портфель полностью оцениваем по cash.
- Ссылочная целостность истории: удаление портфеля с операциями
  запрещено (понятный отказ вместо 500); удаление акции сохраняет
  операции (постоянный снимок идентичности инструмента в записи).
- **Персональный мониторинг акций** (группа 1 задания №4, этап 3):
  личные именованные списки наблюдения и правила уведомлений. Страницы
  (только владелец на сервере; изменения — POST с CSRF):
  - `/watch/lists` — списки наблюдения (POST — создание; то же имя
    списка у другого владельца допустимо);
  - `/watch/lists/<id>` — карточка списка: добавление/удаление
    инструментов (повторное добавление — понятное сообщение, без дубля
    и без 500);
  - `/watch/rules`, `/watch/rules/create`, `/watch/rules/<id>/edit`,
    `/watch/rules/<id>/toggle` (вкл/откл), `/watch/rules/<id>/delete`
    — правила: направление ≥/≤ (оба направления задаются
    отдельными правилами по одному инструменту), положительный точный
    Decimal-порог, источник tinkoff/demo (DEMO помечается бейджем),
    валюта (сравнение без регистра: USD/usd — одна), включённость;
  - `/watch/notifications` — уведомления (пагинация 50, снимок
    инструмента/цены/порога/направления/источника/валюты/времени),
    `POST /watch/notifications/<id>/read` — отметка прочитанным
    (идемпотентно), `POST /watch/notifications/read-all` — отметить все.
  Проверка правил автоматическая: подключена к общему пути записи
  наблюдений `apply_prices` — локальный `collect_prices` и задача
  Celery `update_last_price` дают одинаковое поведение без обязательного
  Redis (сбой одного правила журнализуется и не прерывает цикл).
  Политика уведомлений: создание правила не проигрывает старую историю —
  первое НОВОЕ совместимое наблюдение уведомляет; пока условие
  выполняется — повторов нет; выход повторно взводит, следующий вход —
  новое событие; редактирование/включение пересчитывают исходное
  состояние без уведомления; запоздалая точка не откатывает состояние.
  Удаление правила/инструмента не переписывает доставленные уведомления
  (хранятся снимки).
- Регулярные тесты: `uv run python manage.py test`.

## История цен: локальный периодический сбор (Redis не нужен)

```bash
# Демонстрационный режим без токена (источник помечается как demo
# и отображается как демо-данные, не выдаётся за живые котировки):
python manage.py collect_prices --source demo --interval 10

# Ограниченный пробный запуск (проверка):
python manage.py collect_prices --source demo --interval 2 --max-cycles 3

# Реальный источник (нужен TINKOFF_TOKEN):
python manage.py collect_prices                # источник из PRICE_SOURCE
python manage.py collect_prices --source tinkoff

# Непрерывный сбор: остановка Ctrl-C или SIGTERM — штатная.
# Интервал по умолчанию — настройка PRICE_COLLECT_INTERVAL (сек).
```

- Сбой цикла (сеть, отсутствие токена, недоступность API) журналируется и не
  убивает процесс: следующий цикл повторяет попытку.
- Демонстрационный режим включается только явным выбором источника demo
  (`--source demo` или `PRICE_SOURCE=demo`); незнакомое значение
  `PRICE_SOURCE` даёт ошибку конфигурации при старте, а не молчаливое
  переключение.

## Забираемый каталог и рыночные данные (Tinkoff API)

- `uv run python manage.py add_shares` — загрузка каталога акций.
- Задача `dashboard.tasks.update_last_price` (Celery beat) и локальный
  `collect_prices` используют общий атомарный путь записи: обновляют
  `last_price` и признак `is_trend_high`, фиксируют источник цены
  (`last_price_source`) и добавляют наблюдение в накопленную историю
  через один путь (сбой записи откатывает и кеш, и историю — согласованно,
  на инструмент).
- Ручная цена (через HTML-форму, admin или API) помечается как `manual`;
  происхождение цены определяет сервер — из форм его подделать нельзя;
  очистка цены снимает источник.
- Карточка акции строит график за 180 дней (дневные свечи).
- Без `TINKOFF_TOKEN` эти операции завершаются явной ошибкой
  (`TinkoffTokenMissing`), страница карточки остаётся доступной с сообщением
  «График недоступен: …». Живая интеграция требует действующего токена и
  доступного Tinkoff Invest API.

## Заметки о конфигурации

- Все секреты задаются переменными окружения / файлом `.env` (см. `.env.example`).
  В конфигурации больше нет зашитых паролей базы и пустых секретных ключей
  без объяснения: значения по умолчанию пригодны только для локальной разработки
  и помечены в коде как dev-only.
- Источник накопления цен — `PRICE_SOURCE`: `tinkoff` (умолчание, реальный
  API) или `demo` (ЯВНО включаемый демонстрационный режим с синтетическими
  ценами; наблюдения и текущая цена в этом режиме помечены источником `demo`,
  в интерфейсе показываются как демонстрационные и не выдаются за живые
  котировки). Неизвестное значение даёт ошибку конфигурации при старте.
- Интервал локального сбора цен — `PRICE_COLLECT_INTERVAL` (сек, умолчание
  10; пустое значение считается по умолчанию; нечисловое/неположительное/
  NaN/бесконечность — ошибка конфигурации при старте).
- Ограничение времени внешних запросов Tinkoff API — `TINKOFF_TIMEOUT` (сек,
  умолчание 30). Допускается только конечное положительное значение:
  NaN/бесконечность/ноль/отрицательные дают ошибку конфигурации при старте.
  Дедлайн применяется к самому gRPC-вызову (RPC прерывается клиентом по
  превышению).
- Выход из аккаунта — POST-форма с CSRF (кнопка «Выход» на страницах);
  GET-ссылка выхода удалена намеренно: изменяющая сессию операция не должна
  выполняться небезопасным GET (GET `/userlogout/` отвечает 405).
- REST API: чтение публично, запись (POST/PUT/PATCH/DELETE) — только
  аутентифицированным (`IsAuthenticatedOrReadOnly`) — исправление дефекта
  Д12 из ANALYSIS.md, см. MODERNIZATION.md.

Подробный аудит изменений, проверенные требования и результаты запусков —
в `MODERNIZATION.md`; описание исходного состояния — в `ANALYSIS.md`.

## Стратегии виртуальных сделок

Симулятор стратегий использует сохранённые цены и общий учёт виртуальных
портфелей. История цен, портфели и персональный мониторинг сохранены.

- `/strategies` — создание и список собственных стратегий: свой портфель,
  инструмент, >=/<=, точный порог, BUY/SELL, количество, комиссия,
  источник demo/tinkoff и валюта. Сделки исключительно виртуальные.
- `/strategies/<id>/edit` — настройка; включение, отключение и удаление
  выполняются POST-формами с CSRF. Другие пользователи не имеют доступа.
- `/strategies/<id>/attempts` — журнал и общий результат текущего портфеля;
  `/strategies/attempts` — постоянный журнал владельца, включая удалённые
  стратегии. Старые попытки сохраняют свой портфель и снимки параметров.
- Успешная попытка ссылается на операцию исходного портфеля. Журнал
  портфеля различает ручные и автоматические виртуальные сделки.
- Создание ждёт нового совместимого наблюдения, продолжающееся условие
  не повторяет покупку/продажу; выход и новый вход дают следующую попытку.
  Редактирование/включение перестраивает исходное состояние без сделки.
- Проверка работает автоматически из общего пути записи цен локального
  коллектора и задачи Celery. Время котировки и время исполнения различны:
  это текущая симуляция, а не исторический бэктест.
- Недостаток денег/остатка записывается как отказ. Ошибка записи откатывает
  попытку, операцию, cash и курсор; после восстановления возможен повтор
  без дубля. Оценка без котировки неизвестна; общий P/L портфеля не
  приписывается одной стратегии.
- Идентичность инструмента с настроенной стратегией защищена даже до
  первой котировки. Переименование разрешено, подмена инструмента — нет.

После установки окружения примените миграции, затем запустите сервер:

```bash
DATABASE=sqlite .venv/bin/python manage.py migrate
DATABASE=sqlite PRICE_SOURCE=demo .venv/bin/python manage.py runserver 127.0.0.1:8321
```

В другом терминале из этой же папки можно запустить ограниченный demo-сбор:

```bash
DATABASE=sqlite PRICE_SOURCE=demo .venv/bin/python manage.py collect_prices --source demo --interval 2 --max-cycles 3
```

Demo явно синтетический. Сервер работает до Ctrl+C. Полный набор проверок
окончательной версии: 297 тестов, 47 HTTP-проверок и реальный ограниченный
demo-сбор на отдельной SQLite. Контроль: 1000 → BUY1 по100 → cash900;
цена105 без новой покупки → оценка1005, P/L5, одно уведомление.
Живые Tinkoff, Redis/Celery worker/beat, PostgreSQL и конкурентная нагрузка
не проверялись. SQLite не предоставляет полноценной блокировки строк
SELECT FOR UPDATE; тесты последовательного исполнения не доказывают
поведение под конкурентной нагрузкой.
