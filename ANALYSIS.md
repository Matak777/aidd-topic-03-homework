## 1. Назначение и технологический стек

Investing Demo — веб-приложение для просмотра списка акций и текущих цен, просмотра графика исторических котировок, управления инструментами и работы с API. Котировки и список инструментов берутся из Tinkoff Invest API. Назначение подтверждается веб-интерфейсом `dashboard/templates/dashboard/` и клиентами API в `dashboard/services/`.

## 2. Архитектура и взаимодействие компонентов

Приложение следует стандартной схеме Django MTV. Запрос сначала сопоставляется с маршрутами в `config/urls.py`, затем передаётся в маршруты `dashboard` или `user`. Представления Django либо generic class-based views читают и изменяют записи через ORM; HTML-ответ формируется соответствующим шаблоном. Для создания и изменения акции используется `ModelForm`, построенная по модели `Share`.

REST API подключён под `/api/v1/`. DRF `ModelViewSet` использует общий queryset модели `Share`, сериализатор формирует JSON, а Django ORM выполняет запросы в PostgreSQL. Глобальная конфигурация задаёт пагинацию `LimitOffsetPagination` с размером страницы 100 и backend `django-filter`.

Для внешних рыночных данных есть отдельные сервисы: график запрашивает дневные свечи Tinkoff API за последние 180 дней, а получение текущей цены вызывается периодической Celery-задачей. Celery Beat публикует задачу в Redis, worker выполняет её и сохраняет значения в PostgreSQL. Команда `manage.py add_shares` отдельно загружает список инструментов из Tinkoff API. Подробности запуска инфраструктуры описаны в `README.md`.

## 3. Модель данных и обработка пользовательских запросов

### Сущности и ограничения

1. **`Share` (акция)** — единственная собственная предметная модель (`dashboard/models.py:4-17`):
   - `id` — первичный ключ, автоматически добавляемый Django.
   - `figi` — строка длиной до 255 символов, обязательная и уникальная (`dashboard/models.py:7`).
   - `isin` — обязательная строка длиной до 255 символов (`dashboard/models.py:8`).
   - `name` — обязательная строка длиной до 255 символов (`dashboard/models.py:9`).
   - `ticker` — обязательная строка длиной до 10 символов, уникальная (`dashboard/models.py:10`).
   - `currency` — обязательная строка длиной до 20 символов (`dashboard/models.py:11`).
   - `uid` — обязательная уникальная строка длиной до 255 символов (`dashboard/models.py:12`).
   - `last_price` — `FloatField`, допускающий `NULL` и пустое значение (`dashboard/models.py:13`).
   - `is_trend_high` — nullable boolean, также допускающий пустое значение (`dashboard/models.py:14-16`).
   - `updated_at` — дата и время с `auto_now=True`, nullable и допускает пустое значение (`dashboard/models.py:17`).
   - Название модели в административном интерфейсе задано как «Акция»/«Акции» (`dashboard/models.py:19-21`).

2. **Пользователь** — используется стандартная модель, возвращаемая Django `get_user_model()`; приложение не объявляет собственных полей и связей пользователя (`user/models.py:1-3`). В `settings.py` не задана альтернативная `AUTH_USER_MODEL`.

В модели `Share` нет внешних ключей, поэтому связей между акциями и пользователями (например, портфелей или владельцев записей) код не задаёт. Уникальность ограничена `figi`, `ticker` и `uid`; правила для формата `isin`, допустимых валют, диапазона/точности цены и направления тренда отдельно не определены.

### Запросы и доступ к БД

- Список акций строится generic view из ORM queryset, сортируется по `name` и разбивается на страницы по 100 записей (`dashboard/views.py:20-26`). Детальная страница ищет запись по `id`, затем просит сервис построить график (`dashboard/views.py:29-38`).
- Создание, редактирование и удаление используют Django generic views; создание/редактирование проходят через `ShareModelForm` с `fields = "__all__"`, то есть со всеми редактируемыми полями модели. `updated_at` с `auto_now=True` не является редактируемым полем и в форму не включается (`dashboard/forms.py:6-11`; `dashboard/models.py:17`). Все три операции защищены проверкой `request.user.is_authenticated`; при отказе пользователь перенаправляется на главную страницу (`dashboard/views.py:11-17,41-63`).
- API использует DRF `ModelViewSet` и `Share.objects.all()`, а значит реализует стандартные list/retrieve/create/update/partial_update/destroy операции (`dashboard/api/v1/views.py:16-22`). Фильтр задаёт поля `name` и `ticker`; ordering разрешён по `name` и `ticker`, поиск настроен по `name` с префиксом `$` (`dashboard/api/v1/views.py:10-13,19-22`). В DRF 3.14.0 префикс `$` означает lookup `iregex` — поиск по регистронезависимому регулярному выражению, а не обычный поиск подстроки (`rest_framework/filters.py`, `SearchFilter.lookup_prefixes`). Сериализатор отдаёт `id`, `figi`, `isin`, `name`, `ticker`, `currency`, `last_price`, `is_trend_high`, `updated_at`, но не `uid` (`dashboard/api/v1/serializer.py:6-19`).
- Веб CRUD защищён проверкой входа, однако `ShareViewSet` не задаёт `permission_classes`, а глобальные настройки проекта не переопределяют разрешения DRF (`dashboard/api/v1/views.py:16-22`; `config/settings.py:31-35`). Для DRF `3.14.0` значение по умолчанию — `AllowAny`, и `APIView.permission_classes` берётся из этой настройки (`rest_framework/settings.py`, `DEFAULT_PERMISSION_CLASSES`; `rest_framework/views.py`, `APIView.permission_classes`). Следовательно, при приведённой конфигурации API допускает анонимные запросы, включая операции записи; конкретная доступность извне зависит от сетевого развертывания.
- Django ORM является слоем доступа и для HTML, и для API, и для Celery-задачи. Настроена PostgreSQL база `investing` по адресу `localhost:5432` с пользователем `postgres` (`config/settings.py:91-103`); те же основные параметры указаны для контейнера БД в `docker-compose.yml`.
- Рыночные запросы выполняются не через локально хранимый ряд свечей: сервис графика запрашивает его у внешнего API при открытии страницы (`dashboard/services/graph.py:11-20`). Текущая цена и время приходят из `get_last_prices`; для обновления в модели используется только `price.units` (`dashboard/services/market_data.py:6-11`).

## 4. Основные сценарии и восстановленные требования

Ниже перечислены требования, подтверждённые исходниками отдельных обработчиков и шаблонов. Это описание кода, а не гарантия доступности системы: приложение не запускалось, а внешние интеграции зависят от рабочего PostgreSQL, Redis и действительного токена Tinkoff.

1. **Показывать список акций.** Главная страница выводит тикер, название, ISIN, текущую цену с валютой и цветовую индикацию `is_trend_high`; список сортируется по названию и разбивается на страницы по 100 акций. При пустом списке отображается сообщение об отсутствии акций. Подтверждение: `dashboard/views.py:20-26`; `dashboard/templates/dashboard/list.html:13-34,35-40,53-85`.
2. **Открывать детальную страницу акции.** Переход по тикеру открывает запись по её id; показываются название, последняя цена, валюта и время обновления. Подтверждение: `dashboard/urls.py:14-15`; `dashboard/views.py:29-38`; `dashboard/templates/dashboard/detail.html:10-13`.
3. **Показывать график исторической цены.** При формировании детализации сервис запрашивает дневные свечи за 180 дней по FIGI и строит линейный график Plotly. Подтверждение: `dashboard/views.py:34-38`; `dashboard/services/graph.py:11-36`.
4. **Предоставлять аутентифицированному пользователю операции с акциями через веб-интерфейс.** В интерфейсе доступны добавление, редактирование и удаление; формы основаны на модели и включают все её редактируемые поля. Поле `updated_at` с `auto_now=True` в форму не входит. Успешные изменения перенаправляют на список; удаление требует подтверждения формой. Подтверждение: `dashboard/views.py:11-17,41-63`; `dashboard/forms.py:6-11`; `dashboard/models.py:17`; `dashboard/templates/dashboard/list.html:8-10,41-48`; `dashboard/templates/dashboard/create.html:10-19`; `dashboard/templates/dashboard/delete.html:9-12`.
5. **Требовать аутентификацию для веб-операций изменения данных.** Неаутентифицированный запрос на создание, изменение или удаление перенаправляется на главную; чтение списка и детализации такой проверкой не закрыто. Подтверждение: `dashboard/views.py:11-17,20-38,41-63`.
6. **Предоставлять регистрацию, вход и выход.** Для регистрации предусмотрены поля email и два пароля, проверка совпадения паролей и проверка существования пользователя с таким email; при успешной валидации код создаёт пользователя и передаёт его в `login`. Обработчик входа создаёт `AuthForm`, но не вызывает `form.is_valid()` перед аутентификацией, а обращается к отправленным данным напрямую; при успешной аутентификации входит в сессию и перенаправляет на главную, при неуспехе показывает сообщение. Выход очищает сессию и возвращает на главную. Email при регистрации явно не приводится к нижнему регистру, тогда как в обработчике входа он приводится; нормализация регистра между этими сценариями несогласована. Подтверждение логики: `user/forms.py:8-53,56-70`; `user/views.py:16-33,36-55,58-64`; `user/urls.py:8-10`.

## 5. Дефекты, противоречия, ограничения и неопределённости

### Дефекты и замечания реализации

- **Валидация входной формы не вызывается.** Обработчик POST создаёт `AuthForm(request.POST)` и сразу передаёт данные в `authenticate`, не вызывая `form.is_valid()` (`user/views.py:16-19`). Поэтому валидаторы полей формы, включая проверку формата email и обязательности, в этом обработчике не выполняются; обращения к отсутствующим ключам также могут завершиться ошибкой.
- **Регистрация и вход по-разному обрабатывают регистр email.** Форма регистрации проверяет существование email и передаёт его в `create_user` без явного приведения всего адреса к нижнему регистру (`user/forms.py:30-41,48-51`), а обработчик входа приводит переданный email к нижнему регистру (`user/views.py:16-19`). Для адресов с заглавными символами это может привести к несовпадению имени пользователя при последующей аутентификации; результат проверки повторного адреса с иным регистром также зависит от нормализации модели пользователя и сравнения БД.
- **Конфигурация содержит пустые/неподготовленные значения:** `SECRET_KEY` пуст, `DEBUG=True`, `ALLOWED_HOSTS=[]` (`config/settings.py:6-10`); токен Tinkoff пуст (`config/settings.py:134`). Это не конфигурация для эксплуатации, а без токена запросы к внешнему сервису не могут быть корректно авторизованы.
- **Валидация регистрации может завершаться исключением вместо ошибки формы.** `clean()` напрямую индексирует `cleaned_data` по обязательным ключам (`user/forms.py:30-34`), даже если соответствующие поля не прошли валидацию. Кроме того, представление при любой ошибке формы безусловно читает `form.errors["__all__"]` (`user/views.py:50-55`), хотя ошибка может относиться к отдельному полю.
- **API-сериализатор не включает `uid`, хотя поле модели обязательное и уникальное.** Сериализатор перечисляет поля без `uid` (`dashboard/api/v1/serializer.py:9-19`), а модель объявляет уникальный `uid` без null/blank (`dashboard/models.py:12`). Создание через API поэтому не задаёт этот атрибут корректным значением; фактическое поведение при сохранении зависит от пустого значения, которое ORM присваивает строковому полю, и может привести к конфликту уникальности при последующих записях.
- **Периодическое обновление не обновляет `updated_at`.** Значение цены сохраняется через `QuerySet.update()` с передачей только `last_price` и `is_trend_high` (`dashboard/tasks.py:24-26`). Такой вызов не запускает `auto_now` модели; отображаемое время (`dashboard/templates/dashboard/detail.html:12`) может не соответствовать последнему обновлению цены.
- **Цена теряет дробную часть, если провайдер вернул её отдельно в `nano`.** Сервис сохраняет только `resp.price.units` (`dashboard/services/market_data.py:11`); построение истории также использует только `candle.close.units` (`dashboard/services/graph.py:19-20`).
- **В задаче подавляются ошибки на уровне каждой акции.** Исключения перехватываются и только логируются (`dashboard/tasks.py:12-28`); задача не задаёт повторную попытку и не сообщает вызывающему процессу, что обновление не выполнено.

### Противоречия и ограничения поведения

- Имя расписания Celery `"add-every-5-min"` не соответствует фактическому периоду `10.0` секунд (`config/celery.py:13-17`). В README перечислен запуск Beat, но не разрешено, какое расписание предполагалось; поэтому нельзя считать «раз в пять минут» фактическим требованием.
- Логика `is_trend_high` не задаёт надёжного бизнес-правила «цена растёт». В реализации условие `share.last_price > last_price` записывает `False`, иначе — `True`, то есть равные значения попадают в ветку `True`; исключение при сравнении, например при исходном `NULL`, также приводит к `True` (`dashboard/tasks.py:15-22`). Это поведение реализации, а не подтверждённое требование о росте цены.
- Внешняя история не кэшируется и не хранится локально: график строится запросом к провайдеру на каждом открытии детализации (`dashboard/views.py:34-38`; `dashboard/services/graph.py:11-20`). Доступность графика зависит от Tinkoff API и токена.
- В веб-интерфейсе CRUD закрыт проверкой входа, но у API `ShareViewSet` нет явных `permission_classes` или проверки пользователя (`dashboard/api/v1/views.py:16-22`). С учётом закреплённого DRF `3.14.0` это означает стандартную политику `AllowAny`, а не неопределённую политику (`requirements.txt:16`; исходники DRF 3.14.0 `rest_framework/settings.py` и `rest_framework/views.py`).
- Модель помечает `last_price`, `is_trend_high` и `updated_at` допускающими `NULL`, но отображение не задаёт специального текста для неизвестной цены/тренда; цвет выбирается по truthiness `is_trend_high`, а цена и валюта выводятся рядом (`dashboard/templates/dashboard/list.html:35-40`).
- `add_shares` вызывает `get_or_create` с FIGI и остальными атрибутами одновременно в lookup-параметрах (`dashboard/management/commands/add_shares.py:15-22`). Поэтому не определено ожидаемое поведение при повторном импорте инструмента с уже известным FIGI, но изменившимися данными.
