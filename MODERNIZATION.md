### Критическая находка исходных зависимостей

pip-пакеты **`tinkoff` и `tinkoff-investments` недоступны в PyPI**
(HTTP 404 на `pypi.org/simple/<имя>/` — только наблюдаемый факт о
доступности индекса на момент проверки; причину недоступности он не
устанавливает), а официальный репозиторий `Tinkoff/invest-python` на GitHub
помечен как архив (архивированный статус и последний push датированы
2023-08-06 — наблюдаемые факты; точную дату и причину архивации по этим
данным объяснить нельзя). Установить SDK из PyPI не удаётся: установка
исходного `requirements.txt` с ним не воспроизводима.
Решение — вендоринг (см. `vendor/tinkoff-investments/README.md`):

- upstream: https://github.com/Tinkoff/invest-python, тег `0.2.0-beta50`,
  upstream commit `9d567143e7bd732b1bd952a420c0b743e0c1efa1`;
- каталог `tinkoff/` скопирован без изменений (diff с деревом тега идентичен);
- LICENSE (Apache-2.0) сохранён; добавлен свой `pyproject.toml` (hatchling)
  с обновлёнными совместимыми зависимостями; зависимость `tinkoff==0.1.1`
  (также удалён из PyPI; импортируется только импорт-несущими модулями и не
  используется кодом) убрана.

Проверка вендора на текущем стеке: импорт `tinkoff.invest` (Client,
CandleInterval, Quotation/MoneyValue, ответы API), protobuf-сериализация
roundtrip (`LastPrice` → bytes → ParseFromString) с grpcio 1.84.1 +

Tinkoff API недоступен (нет токена; сервис может быть отключён), все интеграционные

## 3. Исправление дефектов реализации (обособленно от требований)

Ссылки Д* — на ANALYSIS.md. Требования Т1–Т16 сохранены; исправления
отделяют спорное поведение, а не добавляют требования.

- Д2 (токен) + Д3 (дробная часть цены): `dashboard/services/market_data.py`
  — явная проверка токена; цена — `money_to_float(quotation)` =
  units + nano/1e9; `dashboard/services/graph.py` — график использует
  `close.units + close.nano` целиком. Живой API Tinkoff не проверялся —
  тест с заглушкой.
- Д4 («растёт» при равенстве/ошибке — спорное фактическое поведение):
  `dashboard/tasks.py`: рост = `new > previous`; равная цена → False (не растёт);
  первая цена (нет предыдущей) → None (неизвестно). Шаблон
  `dashboard/templates/dashboard/list.html` — нейтральная ячейка
  (без зелёной/красной подсветки) вместо обманчивой красной.
- Д5 (auto_now при `QuerySet.update`): задача передаёт
  `updated_at=timezone.now()` в `update()` (bulk как раньше); тест проверяет.
- Д6 (HTML 500 на несуществующую акцию): `ShareDetailView` —
  `get_object_or_404` → HTTP 404.
- Д7/Д9/Д10 (регистрация): `user/forms.py` — `cleaned_data.get()` вместо
  KeyError; валидаторы пароля применяются; проверка занятого email —
  регистронезависимой (`email__iexact`, без миграции на уникальный индекс —
  остаётся ограничение, см. §7). `user/views.py` — отображение полевых ошибок,
  а не только `__all__` (отрисовка «Enter a valid email address.» на странице).
- Д8 (регистр username): username при регистрации приводится к нижнему регистру
  (вход по email в любом регистре работает; проверено живым POST).
- Д11 (add_shares IntegrityError): поиск по `figi`, остальные поля при
  изменении на стороне API обновляются; сбой внешнего запроса
  (`client.instruments.shares()`) обрабатывается явно (stderr, не traceback);
  тесты на оба случая.
- Д12 (API без аутентификации — исправлен дефект): чтение
  (`GET /api/v1/shares/` и карточка) оставлено публичным; запись
  (POST/PUT/PATCH/DELETE) разрешена только аутентифицированным
  (`IsAuthenticatedOrReadOnly` в `REST_FRAMEWORK`). Полный анонимный CRUD
  был дефектом реализации, а не обязательным требованием Т14 (Т14 описывал
  доступность API, а не модель прав). Проверено тестами (анонимная запись →
  403, чтение → 200, запись под логином → 201/200/204) и живыми HTTP-проверками.
- Выход из сессии — только POST: `LogoutView` (`user/views.py`) разрешает
  только `POST`; кнопка «Выход» в `base.html` переделана на
  `<form method="post">{% csrf_token %}…</form>`. GET `/userlogout/` теперь
  **405** (раньше GET без защиты CSRF завершал сессию — побочный вектор
  CSRF-выхода). Тесты и шаблон обновлены.
- Д14 (последовательный обход + клиент на каждую акцию): задача получает цены
  одним пакетным RPC `get_last_prices(figi_list)` и одним клиентом: **число
  RPC-вызовов не зависит от размера каталога** (один вызов вместо N).
  Объём ответа, число FIGI и время обработки по-прежнему растут с размером
  каталога — прежнее утверждение «размер запроса не зависит от размера
  каталога» было некорректным и исправлено.
- Ограничение времени RPC — настоящий gRPC-дедлайн: SDK не задаёт
  дедлайны на вызовы (проверено по коду сервиса), поэтому
  `dashboard/services/market_data.py` оборачивает стабы
  (`DeadlineStub`, `apply_rpc_deadline(client, timeout)`) и каждый unary/
  stream-метод SDK получает `timeout=` самого gRPC-вызова: RPC прерывается
  клиентом по дедлайну (DEADLINE_EXCEEDED). Применено в
  `get_last_prices`, `services/graph.py`, команде `add_shares`.
  `TINKOFF_TIMEOUT` валидируется до запуска (допускается только конечное
  положительное значение; NaN/inf/0/отрицательные/нечисло → `ImproperlyConfigured`
  в settings, `ValueError` в `validate_timeout`). `run_with_timeout` остаётся
  страховкой локального ожидания (дедлайн + буфер 1 с): прекращение ожидания
  этого фонового потока не тождественно остановке RPC — на этот случай честно
  указывает сообщение об ошибке; основной ограничителем является gRPC-дедлайн.
  Превышение DEADLINE_EXCEEDED, передача дедлайна в транспорт и отсутствие
  накопления потоков/каналов проверены тестами на локальном grpc-сервере
  (живой токен не требуется, транспорт подменён); «живая» проверка против
  реального Tinkoff API не проводилась (нет токена).
- Пароли — посимвольные (strip=False): пароль входа и оба пароля регистрации
  не обрезают граничные пробелы; `save()`/вход используют согласованный
  `cleaned_data` (раньше регистрация сохраняла очищенный, а вход брал
  сырые `form.data` — пароль с пробелами не подходил повторно). В
  `validate_password` передаётся несохранённый кандидат с нормализованными
  email/username — `UserAttributeSimilarityValidator` реально отклоняет
  пароль, совпадающий с email (комментарий, ранее оправдывавший приём такого
  пароля, убран). Тесты: сохранение точного пароля, вход с пробелами, отказ
  обрезанного пароля, несовпадение, «too similar».
- Д16 (покрытие): добавлены регрессионные тесты (см. §4).
- UP-BUG (скрытый дефект API, выявлен при живой проверке): сериализатор
  исходной версии не включал `uid`, а БД требует уникальный `uid` без
  умолчания — второй POST создал запись с пустым `uid`, третий падал
  `IntegrityError` → 500 (воспроизведено живым POST, по журналу сервера:
  `UNIQUE constraint failed: dashboard_share.uid`). Исправление:
  `dashboard/api/v1/serializer.py` включает `uid`; дубликат/отсутствие
  `uid` теперь 400 с сообщением поля (проверено живым POST), тесты обновлены;
  это изменение записано в отличие от ранее задокументированной
  «сериализатора без uid» Т14.

## 7. Непроверенные сценарии и оставшиеся ограничения

Не проверено (препятствия/ограничения среды):
- **Живой Tinkoff Invest API недоступен** (нет действующего токена; официальный
  сервис может быть отключён, SDK заморожен). Все интеграционные требования
  (Т12/Т13/Т3-график, `add_shares`, `update_last_price`, свечи) проверены
  **только тестами с заглушками внешнего API** (mock): это не подтверждение
  работоспособности рыночных данных.
- **Redis/Celery**: Redis в среде не установлен. Проверено реальным запуском:
  beat/worker стартуют и дают явную ошибку соединения с Redis. Полную
  регламентную проверку по 10-секундному интервалу с Redis не делал.
- PostgreSQL-режим (`DATABASE=postgres`) не проверен живым подключением
  (нет Docker/СУБД в среде); конфигурация сохранена.
- Фактическая длительность задачи по большому каталогу не измерялась
  (замер не проводился). Число RPC не зависит от размера каталога
  (пакетный вызов), но объём ответа и время обработки растут с ним.
- `is`-оператор шаблонов (list.html) — новое поведение None-тренда
  регламентировано тестом; для старых версий Django не заявляется
  (нужна 4.1+; в стеке 5.2).
- Поиск API `?search=` остаётся iregex (Д15): regex-спецсимволы могут порождать
  ошибки SQL на уровне СУБД; поведение на SQLite/PostgreSQL не систематически
  проверено (см. Н5 в ANALYSIS.md).
- Email в БД остаётся без уникального индекса (Д10 частично): регламентная
  проверка регистронезависимая в форме, дубликаты на уровне БД не исключены
  (изменение схемы отнесено к индивидуальному рефакторингу, как не переносимое
  на конкретную базу).
- REST API: запись защищена (`IsAuthenticatedOrReadOnly`), но тонкая
  настройка прав (по-объектные permissions, throttling, отдельные роли)
  не настраивалась — сделан только шаг аноним→аутентифицированный (Д12).
- gRPC-дедлайн проверен только на локальном grpc-сервере (подменённый
  транспорт, живой токен не требуется); поведение против реального
  Tinkoff API (в т.ч. реальные коды ошибок трекинга) не проверялось.
- Модель прав HTML-частей не менялась: create/update/delete требуют
  входа как в исходной версии.
- Логирование INFO/ERROR в консоль и файл `app.logs` сохранено; содержимое
  лог-файла при работе Celery-worker с Redis не проверялось (см. выше).
- Локальный dev-режим допускает DEBUG=True и служебный SECRET_KEY: это
  значения по умолчанию, помеченные dev-only; production-чек-лист (секьюрити
  WARN/W018/W020 ANALYSIS.md Д1) снимается только настройкой окружения.
